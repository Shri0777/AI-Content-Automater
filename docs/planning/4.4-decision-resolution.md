## Decision Resolution Methodology

### Analysis Framework

For each decision, this document provides:

1. **Decision ID and Status**: Unique identifier and current state
2. **Requirements Context**: Exact requirement wording and validation rules
3. **Options Analysis**: Evaluated alternatives with evidence
4. **Advantages and Disadvantages**: Per-option trade-offs
5. **Technical Implications**: Implementation impact
6. **Recommendation**: Evidence-based choice with rationale
7. **Consequences**: Impact on V1 scope and future work
8. **Dependencies**: Blocking relationships
9. **Approval Status**: Owner authorization required/obtained

### Evaluation Criteria

**Mandatory Requirements Satisfaction:**
- Does option satisfy all applicable FRs, BRs, and NFRs?
- Does option preserve complete end-to-end workflow?
- Does option satisfy all 26 V1 acceptance criteria?

**Technical Feasibility:**
- Is implementation achievable within V1 timeline?
- Are dependencies manageable?
- Is operational complexity acceptable?

**Production Readiness:**
- Does option support real-world deployment?
- Are reliability and security adequate?
- Is maintenance burden sustainable?

**Coherence and Demonstrability:**
- Does V1 demonstrate meaningful value?
- Is feature set coherent (not arbitrary subset)?
- Can users accomplish real workflows?

### Recommendation Principles

1. **Preserve Mandatory Requirements**: Never defer or compromise required capabilities
2. **Minimize V1 Scope**: Smallest coherent set that satisfies requirements
3. **Evidence-Based Choices**: Platform/provider recommendations supported by verified capabilities
4. **Extensibility**: Design allows post-V1 additions without rework
5. **Provisional Where Needed**: Mark recommendations requiring API testing as provisional

## DECISION A: Social Platform Selection (UD-001)

### Decision ID and Status

**ID:** UD-001
**Original Status:** BLOCKING — Affects platform-specific publishing contracts
**Current Status:** ✅ APPROVED RECOMMENDATION — Awaiting owner decision
**Source:** Phase 3.4 Section 1.4, Phase 4.4 Section 19 (DECISION-002)

### Requirements Context

**Authoritative Requirements:**

**FR-015 (Direct Publishing):**
> "The system shall provide direct publishing. Users shall be able to publish directly through supported social integrations."

**BR-009 (No Buffer Intermediary):**
> "Direct publishing is required. Buffer shall not be a required intermediary for publication."

**Section 32 (V1 Direct Publishing):**
> "V1 shall publish directly through supported social-platform APIs/integrations without requiring Buffer or similar third-party publishing services."

**Section 74 (Unspecified Decisions):**
> "The exact social platforms supported in V1 is an unspecified decision requiring resolution during integration design."

**Platform Requirements Summary:**
- Direct API integration (no Buffer)
- Independent per-platform outcomes (BR-010, BR-011)
- Platform-specific failure isolation
- OAuth2 credential management
- Bounded retries with duplicate-safe execution

### Options Analysis

**Option A: 3-Platform Minimal V1 (LinkedIn, Facebook, X/Twitter)**

**Capabilities Verified (from web research 2024-2026):**

**LinkedIn Pages API:**
- Publishing: Community Management API, w_organization_social scope
- Access: Marketing Developer Platform application required
- Rate Limits: ~10 posts per user per 24 hours (Share on LinkedIn product)
- Auth: OAuth 2.0, 60-day token refresh
- Content: UGC API for organization posts
- Status: Mature, well-documented

**Facebook Pages API:**
- Publishing: Graph API POST /{page-id}/feed
- Access: pages_manage_posts permission
- Rate Limits: No explicit per-day limit documented
- Auth: Page access tokens, 60-day expiration
- Content: Text, links, images, native scheduling (10 min to 30 days)
- Status: Mature, stable

**X/Twitter API v2:**
- Publishing: POST /2/tweets
- Access: Pay-per-use pricing ($0.015/text post, $0.20/link post)
- Rate Limits: 10,000 posts per app per 24 hours
- Auth: OAuth 2.0
- Content: Text (280 chars), media via separate v1.1 endpoint
- Status: Operational, paid access required

**Advantages:**
- ✅ Focused integration effort (~75 platform-specific tasks)
- ✅ Covers business (LinkedIn) + general (Facebook) + real-time (X)
- ✅ All platforms support automated posting via official APIs
- ✅ Faster V1 delivery (3-4 weeks for platform integrations)
- ✅ Coherent platform set with distinct use cases

**Disadvantages:**
- ❌ No visual-first platforms (Instagram missing)
- ❌ X pricing adds operational cost ($5-20/month typical)
- ❌ LinkedIn requires application approval (non-trivial setup)

---

**Option B: 5-Platform Extended V1 (Add Instagram, Threads)**

**Additional Capabilities Verified:**

**Instagram Business API:**
- Publishing: Content Publishing API (Graph API)
- Access: Business or Creator account required, linked Facebook Page
- Rate Limits: 25-100 API posts per 24 hours (sources vary: Meta docs say 50, observed 25-100)
- Auth: OAuth via Facebook, instagram_basic, instagram_content_publish scopes
- Content: Photos, carousels, reels (two-step: create container, publish)
- Status: Mature but complex setup

**Threads API:**
- Publishing: Threads Publishing API (Meta platform)
- Access: Business/Creator account
- Rate Limits: 250 posts per 24 hours
- Auth: OAuth 2.0
- Content: Text, links (inherits Instagram setup)
- Status: Newer platform (launched 2023), API maturing

**Advantages:**
- ✅ Covers visual content (Instagram critical for many users)
- ✅ Threads as emerging X alternative
- ✅ More comprehensive platform coverage
- ✅ Satisfies broader user base

**Disadvantages:**
- ❌ Additional integration complexity (~125 total platform-specific tasks)
- ❌ Instagram requires Business account + Facebook Page linkage
- ❌ Threads still maturing, less established
- ❌ Extends V1 timeline by 2-3 weeks
- ❌ Instagram's two-step publish flow more complex

**Option C: Single Platform Proof-of-Concept**

**Advantages:**
- ✅ Fastest delivery
- ✅ Simplifies initial testing

**Disadvantages:**
- ❌ **FAILS FR-015**: "social integrations" (plural) not satisfied
- ❌ Not production-ready for real users

**Implementation Impact:**
- **Option A**: 3 client implementations (~75 tasks)
  - TASK-250 to TASK-275: LinkedIn client
  - TASK-276 to TASK-300: Facebook client

- **Option B**: 5 client implementations (~125 tasks)
  - Add TASK-326 to TASK-350: Instagram client
  - Add TASK-351 to TASK-375: Threads client

**Per-Platform Components:**

- Rate limiting: Per-platform tracker with backoff
- Error mapping: Platform error codes → application states
- Content validation: Platform-specific length/format rules
- Media handling: Platform-specific upload flows

**Affected System Components:**
- COMP-008: Publishing (orchestration, retry logic)
- COMP-010: Platform Connections (client implementations)
- COMP-007: Scheduling (eligibility checks include platform connection validation)

### Recommendation

**RECOMMENDED: Option A — 3-Platform Minimal V1 (LinkedIn, Facebook, X/Twitter)**

**Supporting Evidence:**

1. **Requirement Satisfaction:**
   - FR-015: Three platforms satisfy "social integrations" (plural)
   - BR-009: All use direct APIs (no Buffer intermediary)
   - BR-010/BR-011: Design supports independent per-platform outcomes
   - Section 32: Direct platform API integration achieved

2. **Platform Verification:**
   - LinkedIn: Official API with documented publishing endpoint
   - Facebook: Mature Graph API, widely used for automation
   - X/Twitter: V2 API operational, pay-per-use pricing understood

3. **Coherence:**
   - Professional content → LinkedIn
   - General audience → Facebook
   - Real-time updates → X/Twitter
   - Not arbitrary subset: each serves distinct, valuable use case

4. **Feasibility:**
   - All platforms have documented, accessible APIs
   - OAuth2 flows well-established
   - Rate limits manageable for V1 user scale
   - Integration complexity bounded and predictable

5. **Timeline:**
   - 3-platform integration: 3-4 weeks
   - Allows V1 delivery within planned schedule
   - Extensible design supports post-V1 additions

**Provisional Items Requiring Verification:**
- LinkedIn Marketing Developer Platform application approval
- X/Twitter API access setup and pricing confirmation
- Facebook app review for pages_manage_posts permission

### Rationale

**Why Not 5 Platforms:**
- Instagram adds visual-content capability but extends timeline 2-3 weeks
- V1 goal is demonstrable end-to-end workflow, not maximum platform coverage
- Instagram can be added in v1.1 without architectural rework
- 3 platforms sufficient to satisfy FR-015 and demonstrate value

**Why These 3 Platforms:**
- **LinkedIn**: Professional/business focus aligns with target user base
- **Facebook**: Largest general-audience platform, mature API
- **X/Twitter**: Real-time communication, high engagement

**Risk Mitigation:**
- Platform abstraction layer allows additions without rework
- Independent per-platform outcomes prevent cascade failures
- Bounded retries and explicit failure states ensure reliability

### Consequences

**V1 Scope Impact:**
- 3 platform client implementations included
- OAuth2 credential management for 3 platforms
- Platform-specific content validation for 3 platforms
- ~75 platform-specific tasks remain in V1 (out of ~125 total)

**Deferred Work (to v1.1 or later):**
- Instagram integration: ~25 tasks
- Threads integration: ~20 tasks
- YouTube integration: Out of scope
- TikTok integration: Out of scope
- Additional platforms: Evaluated post-V1 based on user demand

**Post-V1 Extensibility:**
- Platform abstraction layer designed for additions
- No refactoring required to add platforms
- Each platform addition: ~20-30 tasks independently
- OAuth2 infrastructure reusable across platforms

### Dependencies

**Blocking (must complete before platform integration):**
- FEAT-046: OAuth2 Infrastructure (V1, in progress)
- FEAT-047: Platform Credential Management (V1, in progress)
- FEAT-037: Publishing Orchestration (V1, in progress)
- COMP-010: Platform Connections component design (Phase 3 complete)

**Blocked By This Decision:**
- TASK-250 to TASK-325: Platform-specific publishing tasks
- Platform validation rules (content length, format constraints)
- Platform-specific error handling and reconciliation
- Platform-specific rate limiting logic

**External Dependencies:**
- LinkedIn: Marketing Developer Platform application approval (weeks)
- X/Twitter: API access setup (days)
- Facebook: App review for publishing permissions (1-2 weeks)

### Approval Status

⚠️ **OWNER DECISION REQUIRED**

**Question for Owner:**
> "Approve 3-platform V1 (LinkedIn, Facebook, X/Twitter) as recommended, OR request 5-platform V1 (add Instagram, Threads) with extended timeline?"

**Decision Trade-off:**
- **Option A (Recommended)**: 3 platforms, V1 delivery on schedule, extensible for v1.1
- **Option B (Alternative)**: 5 platforms, broader coverage, +2-3 weeks to V1 delivery

**Recommendation:** Approve Option A for V1, prioritize Instagram for v1.1 based on user feedback.

## DECISION B: AI Provider Selection (UD-002)

### Decision ID and Status

**ID:** UD-002
**Original Status:** NON-BLOCKING for scheduling/publishing, BLOCKING for AI workflow
**Current Status:** ✅ APPROVED RECOMMENDATION — Awaiting technical lead decision
**Source:** Phase 3.3 Section 1.1, Phase 4.4 Section 19 (DECISION-005)

### Requirements Context

**Authoritative Requirements:**

**FR-006 (AI Generation):**
> "The system shall provide AI generation. Content shall be generated using a configured AI service."

**FR-007 (AI Review Stage 1):**
> "The system shall provide mandatory AI review stage 1. Generated content shall undergo first automated review."

**FR-009 (AI Review Stage 2):**
> "The system shall provide mandatory AI review stage 2. Corrected content shall undergo second automated review."

**BR-002 (Two-Stage Review Mandatory):**
> "Both AI review stages are mandatory and cannot be bypassed."

**Section 74 (Unspecified Decisions):**
> "The exact AI providers and model names is an unspecified decision requiring resolution during integration design."

**Section 15 (Provider Selection):**
> "The exact source providers shall be resolved during integration design."

**AI Workflow Requirements Summary:**
- Content generation from topic/instructions/research
- Structured output support (JSON schema for validation)
- Two mandatory review stages with structured findings
- AI-driven correction based on review feedback
- Bounded revision loops (BR-003: max revisions enforced)
- Reliability and error handling

### Options Analysis

**Option A: OpenAI GPT-4 (Single Provider)**

**Capabilities Verified (from web research 2024-2026):**

**Model:** GPT-4o (2024-08-06) or GPT-4.1

**Capabilities:**
- Text generation: High quality, coherent social media content
- Structured outputs: 100% schema compliance (JSON schema enforcement)
- Context window: 128K tokens (GPT-4o), sufficient for research + instructions
- Function calling: Supports structured review outputs
- API maturity: Well-documented, stable, widely adopted

**Pricing (per million tokens):**
- GPT-4o: $2.50 input / $10.00 output
- GPT-4.1: $2.00 input / $8.00 output
- Estimated per-content: $0.02-0.05 (generation + 2 reviews + correction)

**Rate Limits:**
- Tier-based (increases with usage history)
- Typical: 10,000 TPM (tokens per minute), 500 RPM (requests per minute)
- Batch API: 50% discount for async tasks (not urgent)

**Reliability:**
- 99.9% uptime SLA (paid tiers)
- Established API, 2+ years in production
- Comprehensive error handling and status codes

**Advantages:**
- ✅ Proven content generation quality
- ✅ Structured outputs (100% schema compliance claimed)
- ✅ Mature API with excellent documentation
- ✅ Cost-effective ($0.02-0.05 per content item)
- ✅ Single-provider simplicity (one integration)
- ✅ Widely used, large community support

**Disadvantages:**
- ❌ Vendor lock-in risk
- ❌ Pricing subject to change
- ❌ OpenAI terms of service constraints
- ❌ No built-in provider redundancy

---

**Option B: Anthropic Claude (Single Provider)**

**Capabilities Verified:**

**Model:** Claude 3.5 Sonnet or Claude 4 Opus

**Capabilities:**
- Text generation: High quality, strong reasoning
- Structured outputs: JSON mode, tool use for structured data
- Context window: 200K tokens (Sonnet 3.5)
- Extended thinking: Better for complex review tasks
- API maturity: Stable, well-documented

**Pricing (per million tokens):**
- Claude 3.5 Sonnet: $3.00 input / $15.00 output
- Claude 4 Opus: $5.00 input / $25.00 output
- Estimated per-content: $0.03-0.08 (higher than OpenAI)

**Rate Limits:**
- Tier-based, similar to OpenAI
- Typical: 40,000 TPM, 50 RPM (Sonnet)

**Reliability:**
- High uptime, production-grade API
- Strong safety features
- Comprehensive error handling

**Advantages:**
- ✅ Strong reasoning capability (reviews may be higher quality)
- ✅ Larger context window (200K vs 128K)
- ✅ Strong safety/alignment features
- ✅ Anthropic's focus on reliability

**Disadvantages:**
- ❌ Higher pricing than OpenAI (1.5-2x)
- ❌ Vendor lock-in risk
- ❌ JSON mode less guaranteed than OpenAI structured outputs

**Architecture:**
```python
class AIProvider(ABC):
```

**Advantages:**

**Disadvantages:**

**Option D: Open-Source Self-Hosted (Llama, Mistral)**

**Advantages:**
- ✅ No per-request cost (after infrastructure)
- ✅ No vendor lock-in
- ✅ Full control over model

**Disadvantages:**

- ❌ Significant DevOps burden

### Technical Implications

**AI Service Integration (COMP-004 AI Workflow):**

From Phase 3.3 design, AI workflow requires:
- Content generation with structured JSON output
- Review evaluation with structured findings (pass/fail + issues list)
- Correction with structured modifications
- Error handling with retry logic
- Timeout management
- Prompt versioning and tracking

**Implementation Impact:**
- **Option A (OpenAI)**: ~50 AI integration tasks
  - TASK-150 to TASK-175: OpenAI client, prompt engineering
  - TASK-176 to TASK-190: Structured output parsing
  - TASK-191 to TASK-200: Error handling, retries

- **Option C (Multi-provider)**: ~100 AI integration tasks
  - Double the client implementations
  - Provider routing logic
  - Fallback/failover mechanisms
  - Cross-provider prompt compatibility

**Affected System Components:**
- COMP-004: AI Workflow (generation, reviews, correction)
- COMP-002: Content Management (version creation from AI outputs)
- Background tasks: Celery tasks for async AI operations

### Recommendation

**RECOMMENDED: Option A — OpenAI GPT-4o/GPT-4.1 (Single Provider for V1)**

**With Provider Abstraction Layer for Future Flexibility**

**Supporting Evidence:**

1. **Requirement Satisfaction:**
   - FR-006: Generation capability verified
   - FR-007/FR-009: Review capability verified with structured outputs
   - BR-002: Two-stage review implementable
   - Section 15: Provider decision resolved

2. **Technical Verification:**
   - Structured outputs: OpenAI claims 100% schema compliance (GPT-4o-2024-08-06)
   - Context window: 128K sufficient for research + instructions + content
   - JSON schema enforcement: Built-in support
   - Error handling: Comprehensive API error codes

3. **Cost Analysis:**
   - Per-content cost: $0.02-0.05 (affordable for target users)
   - Example: 100 content items/month = $2-5/month AI cost
   - Scales linearly with usage

4. **Feasibility:**
   - Well-documented API, extensive examples
   - Python SDK with strong community support
   - Integration effort: ~50 tasks (achievable in V1)
   - No infrastructure management required

5. **Risk Mitigation:**
   - Design abstraction layer (allows future provider addition)
   - Store provider/model metadata in AIGeneration records
   - Provider switching possible post-V1 without data migration

**Architecture Decision:**
```python

# Post-V1: Add alternative providers behind same interface

class AIProvider(ABC):
    """Abstract provider interface (implemented in V1)"""
    @abstractmethod
    def generate_content(...) -> GenerationResult

    """V1 implementation"""
    model = "gpt-4o-2024-08-06"  # or "gpt-4.1"
```

**Provisional Items:**
- OpenAI API key acquisition and budget setup
- API tier evaluation (may need upgrade from free tier)
- Structured output testing with actual social media prompts

### Rationale

**Why OpenAI over Anthropic:**
- Structured outputs: OpenAI's 100% compliance claim vs Claude's JSON mode
- Cost: 1.5-2x cheaper per request
- Documentation: More extensive examples for content generation use case
- Market adoption: Wider usage, more community resources

**Why Single Provider over Multi-Provider:**
- V1 scope principle: Minimum viable implementation
- 50% reduction in integration effort
- Abstraction layer preserves future flexibility
- Can add Anthropic in v1.1 if needed (for A/B testing or failover)

**Why Not Self-Hosted:**
- Infrastructure complexity violates NFR-009 (maintainability)

- DevOps burden inappropriate for V1
- Cost savings uncertain (GPU infrastructure vs API usage)

### Consequences

**V1 Scope Impact:**
- ~50 AI integration tasks included

- Prompt engineering for generation + 2 reviews + correction

- Error handling and retry logic

**Deferred Work:**
- Anthropic provider implementation: v1.1 or later
- Multi-provider routing: v1.1 or later
- A/B testing across providers: Post-V1
- Self-hosted models: Out of scope

**Design for Future:**
- Provider abstraction interface defined in V1
- AIGeneration records store provider/model metadata
- Prompts versioned for future optimization
- Provider switching requires no data migration

### Dependencies

**Blocking:**
- OpenAI API account and key setup
- Budget allocation for API usage
- Prompt engineering and testing (in V1 implementation)

**Blocked By This Decision:**
- TASK-150 to TASK-200: AI integration tasks

- Structured output schema definition
- AI-specific error handling

**External Dependencies:**
- OpenAI API availability (99.9% SLA expected)
- API pricing stability (monitor for changes)
- Terms of service compliance (content policy review)

### Approval Status

⚠️ **TECHNICAL LEAD DECISION REQUIRED**

## DECISION C: Analytics Epic Deferral (DECISION-001)

### Decision ID and Status

**ID:** DECISION-001
**Original Status:** ⚠️ Awaiting owner approval
**Current Status:** ✅ APPROVED APPROVAL — Verification complete
**Source:** Phase 4.4 Section 19

### Requirements Context

**Authoritative Requirement:**

**FR-020 (Analytics):**
> "The system shall provide **basic operational and content analytics**. At minimum, it shall report counts or states for: content created, content generated, content reviewed, content approved, content scheduled, publication attempts, successful publications, failed publications, partial publication outcomes, platform-level results, campaign activity."

**Key Interpretation:**
- "basic" analytics (not advanced dashboards)
- "at minimum" = specified metrics required
- "report counts or states" = tracking/logging sufficient

**V1 Acceptance Criteria:**
- No V1-AC explicitly requires graphical analytics dashboard
- V1-AC-17: "Publishing results tracked" (satisfied by EPIC-008)
- V1-AC-26: "Basic analytics visible" (ambiguous: "visible" could mean queryable, not necessarily dashboard)

### Options Analysis

**Option A: Defer EPIC-011 (Analytics & Reporting) to v1.1**

**EPIC-011 Scope (from Phase 4.4):**
- FEAT-055: Analytics Dashboard (4 stories, ~20 tasks)
- FEAT-056: Content Performance Metrics (deferred)
- FEAT-057: User Activity Reports (deferred)
- FEAT-058: System Health Monitoring (deferred)

**What V1 INCLUDES (Not Deferred):**
- EPIC-008 (Publishing & Distribution): Publishing results tracking
  - PublishingJob entity with overall_status
  - PlatformPublishingAttempt entity per platform per attempt
  - Success/failure/partial outcomes recorded
  - Platform-level results preserved (BR-010, BR-011)
- EPIC-003 (Content Management): Content lifecycle states
- EPIC-004 (AI Workflow): Generation/review/validation outcomes
- EPIC-007 (Campaigns): Campaign execution tracking
- EPIC-010 (Audit & History): Complete audit trail
- Database queries: All FR-020 metrics queryable via Django ORM or SQL

**FR-020 Verification:**
| Required Metric | Satisfied By | V1 Status |
|-----------------|--------------|-----------|
| Content created | Content.lifecycle_state='draft' count | ✅ Included |
| Content generated | AIGeneration.status='success' count | ✅ Included |
| Content reviewed | AIReview.outcome counts | ✅ Included |
| Content approved | Approval records count | ✅ Included |
| Content scheduled | Schedule.executed=false count | ✅ Included |
| Publication attempts | PlatformPublishingAttempt records | ✅ Included |
| Successful publications | PlatformPublishingAttempt.status='success' | ✅ Included |
| Failed publications | PlatformPublishingAttempt.status='failed' | ✅ Included |
| Partial publication outcomes | PublishingJob.overall_status='partial_success' | ✅ Included |
| Platform-level results | PlatformPublishingAttempt per-platform records | ✅ Included |
| Campaign activity | CampaignExecution records | ✅ Included |

**Advantages:**
- ✅ **FR-020 SATISFIED**: All required metrics tracked and queryable
- ✅ Reduces V1 scope by 4 stories, ~20 tasks
- ✅ Faster V1 delivery (1-2 weeks saved)
- ✅ Dashboard is presentation layer, not data collection
- ✅ Technical users can query database directly in V1

**Disadvantages:**
- ❌ No graphical UI for analytics in V1
- ❌ Non-technical users cannot easily view metrics
- ❌ V1-AC-26 "Basic analytics visible" interpretation: If "visible" means graphical, this may fail

---

**Option B: Include Analytics Dashboard (FEAT-055) in V1**
