## Blocking findings

### 1. Research implementation scope contradicts the authoritative task register

The Phase 5.9 design (Section 4.2) changes Iteration 2 research work to manual research entry and explicitly defers external providers. However, `docs/planning/4.3-technical-tasks-dependencies.md` defines:

- TASK-053: research provider configuration schema, including encrypted credentials and user/provider junction table.
- TASK-054: provider connection API, credential encryption, connection validation, authorization.
- TASK-055: provider-management UI.
- TASK-056: provider-backed query execution and integrations, with provider selection decision UD-001 as a blocker.
- TASK-057: research query/result storage.
- TASK-058: research execution API and background-job support.
- TASK-059: research results UI.
- TASK-060: query refinement and lineage.
- TASK-061–078: research history, platform validation, templates, performance, security, and audit tasks (the register itself consolidates these rather than specifying each task individually).

The design does not provide implementations/contracts for these required provider/query/history/template capabilities. A manual `Research` notes/link model is not equivalent to the authoritative task scope. Treating all 26 research tasks as implemented by this design would be a false completion claim.

### 2. Provider-selection decision is not approved

`docs/planning/4.4-decision-resolution.md` identifies UD-001 as social platform selection and says its status is “APPROVED RECOMMENDATION — Awaiting owner decision”; the consolidated decision register still marks it proposed and owner approval required. The Phase 5.9 design says external providers are blocked by UD-001, but its readiness rationale simultaneously claims there are no unresolved decisions.

The exact decision dependency needs to be corrected. Do not select or integrate a provider by assumption.

### 3. Immutability trigger conflicts with version approval state

The existing `ContentVersion` model has an `is_approved` field. The proposed PostgreSQL trigger rejects every UPDATE on `content_version`, while the broader requirements include version-specific approval behavior. The design does not define how legitimate approval-state changes can occur without violating the immutability invariant.

Resolve whether approval metadata belongs in a separate mutable record/table or whether the invariant is intended to cover only immutable snapshot fields. Do not deploy the blanket trigger until that contract is explicit.

### 4. Existing state-transition endpoint does not match the authoritative API contract

The current `content_transition` implementation is a Django template/redirect view at the content UI URL, not the specified `POST /api/content/:id/transition` JSON endpoint. It catches broad exceptions and returns a redirect rather than structured API errors/updated content. The design calls TASK-046 complete without acknowledging this difference.

The design must explicitly specify whether the API endpoint is in scope and how it coexists with the server-rendered UI.

### 5. Migration/testing safety must be explicit

The previous test attempt reported that the test database `test_ai_content_automater_dev` already exists. No database was changed during this review. Future verification must not delete or recreate this database. Use a reviewed, non-destructive test strategy and report clearly if the existing test database prevents safe execution.

## Required resolution before implementation

1. Update Phase 5.9 so it faithfully maps each in-scope task to an implementable design and acceptance evidence; mark consolidated/underspecified TASK-061–078 items as blockers until broken down sufficiently.
2. Resolve the owner decision/provider-selection dependency (UD-001) or formally authorize a narrower scope through the project's change-control process. Do not silently replace authoritative requirements with manual-only research.
3. Define version immutability and approval metadata so the database invariant does not make legitimate approval workflows impossible.
4. Reconcile the UI transition view with the required API endpoint and define response/error contracts.
5. Produce a task-to-requirement-to-design traceability table and re-evaluate readiness.
