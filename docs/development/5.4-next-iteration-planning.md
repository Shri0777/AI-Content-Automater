## 5. Iteration Objective and Rationale

### Objective

Implement the first business-capable increment:

1. Identity foundation: user model, registration, login, logout, sessions, profiles, authorization controls, CSRF/security controls.
2. Core domain foundation: content model, ownership, initial lifecycle state, basic content CRUD, version/lifecycle groundwork for later workflow stages.

### Rationale

Iteration 1 is the documented next dependency step after the Django foundation:

- Later research, AI, publishing, scheduling, media, analytics, audit, and configuration work all depend on authenticated users and ownership boundaries.
- Content is the central user-owned domain entity for research, generation, review, approval, scheduling, and publishing.
- BR-001 user resource isolation is a foundation invariant for nearly every later feature.

### Entry Criteria for Phase 5.5 Detailed Technical Design

Before application-feature implementation begins, Phase 5.5 should produce a detailed technical design for Iteration 1 that resolves or explicitly bounds:

1. User model strategy:
   - Whether to use Django's built-in User, a custom user model, or an app-specific profile model.
   - How this interacts with already-applied default Django auth migrations.
   - Whether a fresh development database or migration reset would be required. Any destructive database action requires explicit authorization.

2. Authentication mechanism:
   - Phase 3.1 recommends Django session authentication for V1.
   - Phase 3.2 records DD-NEW-034 as unresolved and recommends JWT.
   - Phase 4.5 mitigation says start with Django session auth and defer OAuth2.
   - Phase 5.5 must reconcile this for Iteration 1 without claiming owner approval where none exists.

3. API/UI approach:
   - Phase 4.3 describes API endpoints and frontend forms.
   - Existing foundation has no frontend framework or API framework.
   - Phase 5.5 must decide whether Iteration 1 uses Django views/templates, Django REST endpoints, or another documented approach consistent with the architecture.

4. Password reset and email behavior:
   - US-002 and TASK-005 through TASK-008 are inside TASK-001 through TASK-031.
   - A real email provider is not selected for Iteration 1. Phase 5.5 must define a safe development-mode reset-token delivery approach or explicitly defer password reset if authorized by planning.

5. Content schema:
   - Requirements leave exact database schema to design.
   - Phase 3.2 provides broad entities; Phase 4.3 task fields are task-level planning.
   - Phase 5.5 must define the initial schema, lifecycle state vocabulary, constraints, and migration plan.

6. Test framework:
   - Iteration 1 introduces business behavior and must include automated tests.
   - Phase 5.5 must choose the project test approach and commands.

## 12. Testing and Security Requirements

Minimum test expectations for Iteration 1:

- Model and migration tests for user/content schema constraints.
- Registration validation tests.
- Password hashing verification.
- Login/logout/session tests.
- Authorization negative tests for cross-user access.
- CSRF tests for state-changing operations.
- Content creation/editing validation tests.
- Lifecycle-state validation tests for included transitions.
- Tests proving no password hashes, secrets, or tokens are exposed in normal responses/logs.

Security expectations:

- No real credentials committed.
- `.env` remains ignored.
- Authentication errors must not disclose account existence.
- Passwords must use Django secure password hashing.
- Server-side authorization must be enforced before resource access.
- CSRF middleware/settings must protect state-changing session-authenticated requests.
- Session cookie/security settings must be explicit for development vs production.
- Logs must not contain passwords, reset tokens, API keys, or raw secrets.
