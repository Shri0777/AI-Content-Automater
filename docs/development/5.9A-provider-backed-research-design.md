## 3. Proposed architecture

Use a provider-neutral domain model and a small adapter boundary. Avoid a large plugin framework or provider-specific conditionals scattered through views.

### 3.1 Domain entities

**ResearchProviderDefinition** (catalog/configuration, not a secret): stable provider code and display name; adapter identifier and capability metadata; enabled/disabled flag managed by deployment/admin policy; configuration schema/version; no user credential values.

**UserResearchProviderConnection**: owner FK; provider definition FK/code; encrypted credential payload or reference to a secret store; non-secret configuration JSON validated against an allowlist/schema; connection status, last validation time, sanitized last error code; created/updated timestamps; unique owner/provider identity unless product requirements explicitly allow multiple accounts; never return secret material through read APIs or logs.

**ResearchQuery**: owner FK; selected provider connection(s); normalized query and safe filters; status (queued/running/succeeded/partial/failed/cancelled); started/completed timestamps, bounded retry metadata, sanitized error code; optional parent query for refinement lineage; idempotency key or request fingerprint with owner scope.

**ResearchResult**: query FK and provider/source identifiers; title, snippet/summary, canonical URL, source/publisher, published time when supplied, retrieved time, rank; safe attribution and provider metadata in a bounded JSON field; deduplication key (normalized canonical URL where possible); no unbounded raw response blobs by default; store only fields needed for attribution, display, audit, and later workflows.

**ResearchContentAssociation**: research result or saved research item FK, content FK, associated_by FK, timestamp, optional relevance note; enforce same-owner association server-side and with appropriate database constraints where feasible.

Manual notes can be represented as a separate user-created research item or explicit manual source type; they must not masquerade as provider query results.

### 3.2 Adapter contract

Define a typed provider interface with operations equivalent to:
- validate a connection/credential without disclosing the credential
- execute a bounded query using provider-supported parameters
- normalize provider-specific responses to a shared result DTO
- map provider failures to safe, finite internal error categories
- expose declared capabilities and limits

The domain service handles authorization, query persistence, timeout/retry policy, deduplication, audit events, and result storage. Provider adapters handle HTTP/API specifics. Views must not call providers directly.

### 3.3 Execution model

- A user can select only providers connected to their own account and enabled by the system.
- Validate and normalize input before network calls.
- Apply request timeout, result-count cap, response-size cap, and per-user/provider rate limits.
- Persist the query before execution so failed and partial attempts remain diagnosable.
- If execution is asynchronous, return a query identifier and expose owner-scoped status/results endpoints. Do not add Celery/Redis unless the approved architecture and current iteration plan explicitly include them; a synchronous bounded implementation can be used only if it satisfies response-time and reliability requirements.
- Treat multiple providers independently; one provider's failure must not erase successful results from another.
- Retry only transient failures, with a bounded attempt count and backoff. Never retry invalid credentials, validation errors, or other permanent failures.
- Make repeated requests safe using idempotency or a documented duplicate policy.
- Preserve refinement lineage; a refined query creates a new query and does not overwrite the original.
- Store sanitized failure codes and operational correlation IDs; never log keys, authorization headers, raw secret-bearing payloads, or sensitive request URLs.

## 4. Security requirements

1. **Credential encryption:** Use authenticated encryption with a key supplied by environment/secret management and separate from the database. Document rotation and decryption failure behavior. Do not invent a hard-coded encryption key or reuse Django SECRET_KEY without an explicit reviewed key-management design.
2. **Credential API behavior:** create/update accepts secrets; read/list responses expose only configured status and masked metadata. Delete removes the connection and makes future execution impossible. No secret is re-displayed.
3. **Ownership:** all provider connection, query, result, history, and association operations are owner-scoped. Cross-user IDs must not reveal existence or contents.
4. **SSRF prevention:** RSS URLs are an attack surface. Reject loopback, private, link-local, multicast, reserved, and metadata-service destinations; validate every redirect target; limit redirects, DNS/IP resolution, ports, schemes, response sizes, and timeouts; defend against DNS rebinding where feasible. Do not fetch arbitrary user-supplied URLs without these controls.
5. **XML safety:** disable external entities and DTD processing; impose feed item and document size limits.
6. **Outbound API safety:** HTTPS only unless a documented provider exception exists; do not forward user-controlled headers or URLs to providers; validate endpoint hosts against adapter configuration.
7. **Data minimization:** persist only needed results and provider attribution; set retention/deletion expectations based on provider terms.
8. **Rate limiting and audit:** enforce per-user/provider request budgets and log connection changes, executions, and failures without credentials.
9. **Terms/licensing:** before enabling each provider, record the relevant current plan, API terms, attribution rules, retention rules, commercial-use restrictions, and budget owner. Do not assume API availability implies permission to store or reuse full article content.

## 5. API contract proposal

Exact paths and response shapes remain subject to the project's API design conventions. Proposed resources:
- /api/research-providers: list available providers and the current user's connection status; never return secrets.
- /api/research-providers/connections: create/list owner-scoped connections.
- /api/research-providers/connections/{id}: retrieve safe metadata, validate, or delete a connection; no secret retrieval.
- /api/research/queries: create/execute a query, return query status and identifier.
- /api/research/queries/{id}: retrieve owner-scoped status/metadata.
- /api/research/queries/{id}/results: paginated owner-scoped results.
- /api/research/queries/{id}/refine: create a child query linked to its parent.
- /api/research/results/{id}/associations or the established content API association route: associate selected results to owned content.

For every endpoint specify request schema, response schema, authorization, validation, status codes, rate limits, idempotency behavior, and error codes in the detailed design before coding. Do not treat this proposal as a finalized API contract.

## 6. Required test matrix

- Adapter contract tests for each selected provider using deterministic fixtures; unit tests must not require live API keys or network access.
- Credential encryption/decryption, wrong-key behavior, key absence, masked serialization, and log redaction.
- Connection CRUD and connection validation with owner isolation.
- Successful query, empty results, malformed response, provider timeout, rate limit, invalid credentials, provider outage, partial success across providers, and bounded retry behavior.
- Normalization, canonical URL deduplication, attribution, result caps, and safe metadata storage.
- Query history, refinement parent/child lineage, and no overwriting original query/results.
- SSRF checks including localhost/private/link-local IPs, redirects to private addresses, disallowed schemes/ports, DNS/IP edge cases, oversized feeds, XML entities, and timeout enforcement.
- Per-user rate limits, pagination, duplicate request/idempotency behavior, and cross-user IDOR tests.
- Database migration tests against PostgreSQL and non-destructive migration checks.
- Regression suite for existing users/content behavior.
- Integration smoke tests against real providers are opt-in and require owner-provided credentials; do not report them passing when they were not run.
