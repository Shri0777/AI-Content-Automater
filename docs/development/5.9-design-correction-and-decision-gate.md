## Purpose

## Verified blockers

### B1 — Research scope and task-register mismatch

**Owner direction recorded on 2026-10-14:** Path A — full provider-backed research scope. This resolves the iteration-scope choice only. It does not approve any exact provider, pricing plan, licensing assumption, credential strategy, or implementation detail. See `docs/development/5.9A-provider-backed-research-design.md` for the provider decision proposal.

The task register in `docs/planning/4.3-technical-tasks-dependencies.md` labels TASK-053 as research provider configuration, TASK-054 as provider connection API, TASK-055 as provider UI, TASK-056 as query execution with provider integrations, TASK-057 as result storage, TASK-058 as execution API, TASK-059 as result UI, TASK-060 as refinement, and TASK-061–078 as additional research/history/validation/template/security work.

The Phase 5.9 design instead implements manual notes/links and defers provider integrations. These scopes are not equivalent. Requirements also state FR-005 as: “collect research information from configured sources” (see `docs/Requirements/REQUIREMENTS.MD`).

**Resolution:** The owner selected **Path A — full provider-backed research scope** and **A1 — RSS/Atom + GNews as the proposed initial adapter set** on 2026-10-14. Do not mark TASK-053–078 complete under a manual-entry-only implementation. Credential/security contracts, API contracts, task breakdown, and live/commercial activation gates remain unresolved. Follow `docs/development/5.9A-provider-backed-research-design.md`.

### B2 — UD-001 is still proposed

In `docs/planning/4.4-decision-resolution.md`, UD-001 is the social-platform selection decision, not a research-provider selection decision. Its consolidated decision register still marks it “Proposed” and says owner approval is required. The Phase 5.9 design's claim that research providers are blocked by UD-001 is therefore not supported by the decision register's stated meaning.

**Resolution:** UD-NEW-RESEARCH-001 now records the owner's A1 selection (RSS/Atom + GNews) as the proposed initial adapter set. This does not approve a paid plan, commercial use, or production activation. Keep UD-001 reserved for social-platform selection. See `docs/planning/4.4-decision-resolution.md` and `docs/development/5.9A-provider-backed-research-design.md`.

### B3 — Version snapshot immutability versus approval state

The existing `ContentVersion` model contains `is_approved`. A database trigger that rejects every UPDATE to `content_version` would also reject changing that field. The requirements state that approval is tied to a specific content version and that the system must not publish an obsolete approved version after a newer unapproved version becomes current.

**Resolution:** Preserve immutable version content while making approval state/version-specific without mutating the immutable snapshot. Design and document the approval representation and migration path before implementing the trigger. Do not add a blanket UPDATE trigger until its compatibility with approval operations is demonstrated by tests.

### B4 — Lifecycle API contract

The task register defines TASK-046 as `POST /api/content/:id/transition`, accepting `target_state` and returning updated content while enforcing ownership and transition rules. The current implementation is a server-rendered UI route at `/content/<pk>/transition/` that redirects. It may serve the UI, but it does not by itself satisfy the specified JSON API contract.

**Resolution:** Decide and document whether the JSON API is in scope for this iteration. If it is, implement it separately or clearly share a tested service layer with the UI route; define success/error status codes and response schemas. Do not call TASK-046 complete solely because the UI route exists.

### B5 — Task detail is insufficient for a blanket “33 tasks ready” claim

The task register itself consolidates TASK-061–078 instead of giving each task an independently testable specification. The Phase 5.9 document also reports 33 tasks ready while deferring several capabilities those task IDs represent.

**Resolution:** Break the in-scope tasks into implementable units with acceptance criteria, dependencies, migration effects, authorization rules, and test evidence. Mark underspecified tasks as blocked instead of asserting they have concrete designs.

## Implementation gate

Implementation may start only after:

1. The owner decision on research scope is explicitly recorded.
2. Provider set A1 is recorded; production/commercial activation remains separately gated on explicit terms/budget approval, and the credential/security/API contracts must be specified.
3. Version content immutability and version-specific approval have a compatible design.
4. TASK-046's UI/API interpretation is explicit.
5. A traceability table maps each in-scope task to requirement(s), code/design location, migration, authorization boundary, and verification test.
6. The corrected design's readiness verdict matches the evidence and lists any remaining blockers.
