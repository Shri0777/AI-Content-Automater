## 12. INCREMENT-SPECIFIC RISK REGISTER

### 12.1 Risks

**R-I0-01: Python Version Mismatch**
- **Cause:** System Python incompatible with Django requirements
- **Impact:** Medium — project setup fails
- **Likelihood:** Low
- **Mitigation:** Verify Python 3.10+ during Phase 5.2, use virtualenv
- **Detection:** Django installation will fail with version error

**R-I0-02: PostgreSQL Not Available**
- **Cause:** PostgreSQL not installed or not running
- **Impact:** Medium — cannot complete database setup
- **Likelihood:** Low (can use SQLite fallback for initial development)
- **Mitigation:** Document both PostgreSQL and SQLite configuration options
- **Detection:** psycopg2 connection error on first migrate

**R-I0-03: Database Credentials Incorrect**
- **Cause:** PostgreSQL user/password/database name misconfigured
- **Impact:** Low — correctable via .env file
- **Likelihood:** Medium (common setup issue)
- **Mitigation:** Provide clear .env.example, document setup steps
- **Detection:** "authentication failed" database error

**R-I0-04: Port 8000 Already in Use**
- **Cause:** Another service running on default Django port
- **Impact:** Low — use different port
- **Likelihood:** Low
- **Mitigation:** Document how to specify custom port
- **Detection:** "Address already in use" error on runserver

**R-I0-05: Settings Misconfiguration**
- **Cause:** SECRET_KEY missing, DEBUG misconfigured, ALLOWED_HOSTS wrong
- **Impact:** Medium — security risk or runtime errors
- **Likelihood:** Low (if following established patterns)
- **Mitigation:** Use secure defaults, require .env file, document all required settings
- **Detection:** ImproperlyConfigured exceptions

**R-I0-06: Scope Creep**
- **Cause:** Temptation to add User model, authentication, or feature logic
- **Impact:** High — violates iteration boundaries
- **Likelihood:** Medium (common when setting up projects)
- **Mitigation:** Explicit out-of-scope list (Section 7.4), Phase 5.2 review
- **Detection:** Files created outside expected foundation scope

### 12.2 Risk Mitigation Summary

**High Priority Mitigations:**
1. Document clear environment setup steps
2. Provide .env.example with all required variables
3. Use Django's secure defaults
4. Enforce iteration scope boundaries during Phase 5.2 review

**Acceptable Risks:**
- Python version issues (detectable early, standard resolution)
- Database configuration issues (well-documented, common troubleshooting)

## 13. PHASE 5.2 DESIGN QUESTIONS

**Technical Decisions Required for Implementation:**

### 13.1 Project Naming

**Question:** What should the Django project be named?

**Context:** Django requires a project name for `startproject` command

**Options:**
1. `content_automater` (snake_case, matches Python conventions)
2. `automater` (short, simple)
3. `ai_content_automater` (descriptive, matches full product name)

**Recommendation:** Defer to Phase 5.2, suggest `content_automater` for clarity without excessive length

**Impact:** Low — naming choice doesn't affect functionality

### 13.2 Django App Structure

**Question:** How should Django apps be organized initially?

**Context:** Django uses apps for modular organization

**Options:**
1. Create placeholder apps for planned epics (users, content, ai_workflow, etc.) in Iteration 0
2. Wait to create apps until their respective iterations
3. Create single "core" app as placeholder

**Recommendation:** Create no apps in Iteration 0 — defer app creation to feature iterations (Iteration 1: users app, content app)

**Rationale:** Apps should contain functionality, not be empty placeholders

**Impact:** Low — apps easily added later

### 13.3 Settings Organization

**Question:** Should settings use split files or environment-based single file?

**Context:** Django supports multiple settings patterns

**Options:**
1. Split settings: base.py, development.py, production.py (Django best practice)
2. Single settings.py with environment variable control
3. Django-environ library for env-based config

**Recommendation:** Split settings (option 1) — matches Django best practices, clearly separates dev/prod concerns

**Impact:** Medium — affects configuration management approach

### 13.4 Database Choice for Iteration 0

**Question:** Use PostgreSQL or SQLite for initial development?

**Context:** Requirements specify PostgreSQL for production, SQLite acceptable for dev

**Options:**
1. PostgreSQL from start (matches production)
2. SQLite for Iteration 0, switch to PostgreSQL in Iteration 1
3. Support both via configuration

**Recommendation:** PostgreSQL from start (option 1) — V1-AC-24 requires PostgreSQL production support, minimize environment differences

**Impact:** Low — Django ORM abstracts database differences

### 13.5 Secret Key Management

**Question:** How should SECRET_KEY be generated and managed?

**Context:** Django requires SECRET_KEY, must not be in source control

**Options:**
1. Generate during setup, store in .env file (manual)
2. Auto-generate on first run if missing
3. Provide .env.example with placeholder, require manual generation

**Recommendation:** Option 3 — .env.example with clear instructions, manual generation via `django.core.management.utils.get_random_secret_key()`

**Impact:** High — security-critical configuration

### 13.6 Dependencies Specification

**Question:** How to specify Python dependencies?

**Context:** Need reproducible environment

**Options:**
1. Single requirements.txt
2. Split requirements: base.txt, development.txt, production.txt
3. pyproject.toml and Poetry
4. Pipfile and Pipenv

**Recommendation:** Split requirements.txt (option 2) — matches Django conventions, clear dev/prod separation, no additional tools required

**Impact:** Low — standard practice
