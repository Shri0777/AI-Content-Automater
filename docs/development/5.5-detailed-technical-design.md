### DECISION 1: User Model Strategy

**Context:**
Django's default auth migrations are already applied. Requirements mandate user authentication (FR-001), authorization (FR-002), and resource ownership (BR-001). The user model is the foundation for all user-owned entities.

**Constraint:**
Django best practice recommends custom user models from the start, but default `django.contrib.auth.User` migrations are already applied (auth.0001_initial through auth.0012_alter_user_first_name_max_length).

**Options Evaluated:**

**Option A: Use Django's default `django.contrib.auth.User`**
- ✅ **Advantages:**
  - No migration complications (already applied)
  - Django admin works immediately
  - Standard Django authentication patterns
  - Fastest path to working authentication
- ❌ **Disadvantages:**
  - Limited field customization without OneToOne profile model
  - Username + email model (we only want email)
  - Harder to extend user fields later

**Option B: Create custom user model, reset development database**
- ✅ **Advantages:**
  - Clean email-only authentication
  - Direct field control
  - Easier future extensions
- ❌ **Disadvantages:**
  - **Requires destructive database operation** (drop/recreate `ai_content_automater_dev`)
  - Loses Django default migrations baseline
  - Higher risk for development environment

**Option C: Use default User + Profile model (OneToOne)**
- ✅ **Advantages:**
  - Preserves existing migrations
  - Extensible via Profile model
  - Separation of auth vs business data
- ❌ **Disadvantages:**
  - Two-table pattern (User + UserProfile)
  - Username field remains (can ignore it, use email for login)
  - Slightly more complex queries

**Recommendation: Option C — Default User + Profile Model**

**Rationale:**
1. **Non-destructive:** Preserves Iteration 0 accepted baseline
2. **Safe:** No database drops or migration resets required
3. **Requirements-compliant:** Satisfies FR-001, FR-002, BR-001 without modification
4. **Extensible:** UserProfile model can hold business fields (role, preferences, etc.)
5. **Standard Django:** Admin, auth middleware, password hashing all work immediately

**Implementation Approach:**
- Keep `django.contrib.auth.User` (email as username, username field ignored)
- Create `users` Django app
- Add `UserProfile` model: OneToOne to `User`, owner-specific business fields
- Use `User.email` for authentication
- Use `UserProfile.role` for application roles (User, Administrator)
- Authorization checks reference `request.user` and `request.user.profile.role`

**Migration Impact:**
- New migrations: `users` app initial migration (UserProfile model only)
- No modifications to existing `auth.*` migrations
- Development database: safe (add-only migrations)

**Approval Status:** 🔶 **REQUIRES OWNER APPROVAL**

**Justification:** This is a fundamental structural decision. While Option C is technically sound and non-destructive, the user model strategy affects all future user-owned entities and should be explicitly approved before implementation.

### DECISION 2: Authentication Mechanism

**Context:**
Phase 3.1 recommends Django session authentication for V1. Phase 3.2 records DD-NEW-034 as unresolved and mentions JWT. Phase 4.5 mitigation says start with Django session auth and defer OAuth2.

**Source Analysis:**
- **Phase 3.1 (Architecture):** "Django session-based authentication for V1 web application"
- **Phase 3.2 (Database/API):** "DD-NEW-034: API authentication pattern (JWT vs sessions) — UNRESOLVED"
- **Phase 4.5 (Release Plan):** "Start with Django session authentication; defer OAuth2/social login"

**Conflict:** Phase 3.2 flagged JWT as unresolved, but Phase 3.1 and 4.5 recommend Django sessions.

**Options Evaluated:**

**Option A: Django Session-Based Authentication**
- ✅ **Advantages:**
  - Standard Django pattern (minimal added dependencies)
  - Built-in CSRF protection
  - Secure cookie-based sessions
  - Works immediately with Django views/templates
  - Stateful server-side session management
- ❌ **Disadvantages:**
  - Server-side session storage required
  - Not ideal for pure API clients (mobile apps)
  - CSRF tokens required for state-changing operations

**Option B: JWT (JSON Web Tokens)**
- ✅ **Advantages:**
  - Stateless authentication
  - Good for API-first architectures
  - Works well for mobile/SPA clients
- ❌ **Disadvantages:**
  - Requires additional dependency (djangorestframework-simplejwt or similar)
  - Token invalidation complexity (logout, password change)
  - Additional security considerations (token storage, XSS, expiry)
  - Deviates from Django defaults

**Option C: Hybrid (Sessions for web, JWT for API)**
- ✅ **Advantages:**
  - Best of both worlds
- ❌ **Disadvantages:**
  - Dual authentication complexity
  - Premature for V1 scope
  - No Iteration 1 mobile client requirement

**Recommendation: Option A — Django Session-Based Authentication**

**Rationale:**
1. **Requirements compliance:** FR-001 does not mandate JWT or API-first approach
2. **Architecture alignment:** Phase 3.1 explicitly selected Django sessions for V1
3. **Iteration 1 scope:** Authentication, content CRUD — all achievable with Django views/templates
4. **Simplicity:** Minimal dependencies, standard Django security model
5. **Deferral support:** Phase 4.5 explicitly defers complex auth patterns
6. **CSRF protection:** Built-in (required by FR-027, Section 53)

**Implementation Approach:**
- Use Django's `django.contrib.auth` middleware
- Session-authenticated views
- CSRF tokens for POST/PUT/DELETE operations
- Login view: POST `/auth/login/` (username=email, password)
- Logout view: POST `/auth/logout/`
- Session cookie: `HttpOnly`, `Secure` in production, `SameSite=Lax`

**Future Extensibility:**
JWT can be added later for API clients if requirements emerge (not Iteration 1 scope).

**Approval Status:** ✅ **APPROVED BY EXISTING DECISIONS**

**Justification:** Phase 3.1 and Phase 4.5 explicitly selected Django session auth for V1. This decision aligns with approved architecture. Phase 3.2's JWT mention was flagged as unresolved but not selected. No additional owner approval required.

### DECISION 3: API/UI Approach

**Context:**
Phase 4.3 describes endpoints (e.g., `POST /api/auth/register`). Existing foundation has no API framework or frontend framework. Iteration 1 must deliver functional authentication and content CRUD.

**Requirements Analysis:**
- FR-001: Authentication (user can log in)
- FR-003, FR-004: Content creation, editing
- V1-AC-01, V1-AC-03: Users can authenticate, users can create content
- No requirement mandates REST API or frontend framework choice

**Options Evaluated:**

**Option A: Django Views + Templates (Server-Side Rendering)**
- ✅ **Advantages:**
  - Zero additional dependencies
  - Standard Django pattern
  - Fast development for Iteration 1
  - Works with Django sessions immediately
  - CSRF protection built-in
- ❌ **Disadvantages:**
  - Traditional request-response (not SPA)
  - Limited frontend interactivity (acceptable for V1)

**Option B: Django REST Framework (API-first)**
- ✅ **Advantages:**
  - Clean API separation
  - Frontend framework flexibility
  - Good for future mobile clients
- ❌ **Disadvantages:**
  - Requires DRF dependency
  - Need separate frontend (React/Vue/etc.) or API-only (no UI)
  - Iteration 1 scope includes working UI (not just API)
  - Additional complexity

**Option C: Hybrid (Django views for auth, DRF for content API)**
- ✅ **Advantages:**
  - Flexible per-feature
- ❌ **Disadvantages:**
  - Dual patterns in Iteration 1
  - Premature optimization
  - Inconsistent authentication between views and API

**Recommendation: Option A — Django Views + Templates**

**Rationale:**
1. **Iteration 1 scope:** Working authentication + content CRUD, not API architecture
2. **Simplicity:** Satisfies acceptance criteria with zero added dependencies
3. **Django alignment:** Uses Django's built-in view/template system
4. **Session auth compatibility:** Perfect fit for session-based authentication
5. **Testability:** Django test client works directly
6. **CSRF built-in:** Required by FR-027

**Implementation Approach:**
- Django views for authentication: `LoginView`, `LogoutView`, registration view
- Django forms for validation
- Django templates for UI (minimal Bootstrap or similar for basic styling)
- Content views: list, create, detail, edit, delete
- URL patterns: `/auth/login/`, `/auth/register/`, `/content/`, `/content/create/`, `/content/<id>/`, etc.
- Authorization: `@login_required` decorator, ownership checks in views

**Templates:**
- `base.html` (base layout, navigation)
- `auth/login.html`, `auth/register.html`
- `content/list.html`, `content/create.html`, `content/detail.html`, `content/edit.html`

**Future Extensibility:**
DRF can be added later for API clients without changing Django views (separate `/api/` namespace).

**Approval Status:** ✅ **APPROVED AS IMPLEMENTATION CHOICE**

**Justification:** Iteration 1 scope is to deliver working authentication and content management. Django views/templates is the standard Django approach and satisfies all Iteration 1 acceptance criteria. This is an implementation choice within approved architecture, not a product direction change.

### DECISION 4: Password Reset and Email Behavior

**Context:**
TASK-005 through TASK-008 are in Iteration 1 scope (part of TASK-001 to TASK-031). US-002 (Password Reset) requires secure token-based reset. Requirements do not specify an email provider for V1.

**Constraint:**
- No email provider configured
- TASK-005 to TASK-008 create password reset token model, generate tokens, send reset emails, validate tokens
- Development environment needs safe behavior

**Options Evaluated:**

**Option A: Implement password reset with console email backend (development)**
- ✅ **Advantages:**
  - Satisfies TASK-005 to TASK-008 functionally
  - Safe for development (emails logged to console)
  - Production email provider deferred (configuration-only change later)
  - Token generation, expiry, validation all testable
- ❌ **Disadvantages:**
  - Real email delivery deferred to production configuration

**Option B: Skip password reset entirely in Iteration 1**
- ✅ **Advantages:**
  - Simplifies Iteration 1
- ❌ **Disadvantages:**
  - **Violates Phase 5.4 approved scope** (TASK-005 to TASK-008 are in TASK-001 to TASK-031)
  - Removes US-002 from Iteration 1 without authorization

**Option C: Integrate real email provider (SendGrid, AWS SES, etc.)**
- ✅ **Advantages:**
  - Fully functional password reset in development
- ❌ **Disadvantages:**
  - Requires external service selection (not in Phase 4.4 approved decisions)
  - Adds dependency and configuration complexity
  - Premature for development-only Iteration 1

**Recommendation: Option A — Console Email Backend (Development)**

**Rationale:**
1. **Scope compliance:** Implements TASK-005 to TASK-008 as planned
2. **Safe development:** No real emails sent, tokens logged to console for testing
3. **Production-ready structure:** Email sending isolated in reusable service, provider swappable via settings
4. **Testable:** Token generation, expiry (30 minutes), single-use validation all testable
5. **Requirements satisfied:** FR-001 (authentication includes password recovery mechanism)

**Implementation Approach:**
- **Model:** `PasswordResetToken` (token, user FK, created_at, expires_at, used_at)
- **Token generation:** Cryptographically secure random token (32 bytes hex), expires in 30 minutes
- **Email backend (development.py):** `EMAIL_BACKEND = 'django.core.mail.backends.console.EmailBackend'`
- **Email backend (production.py):** Configured SMTP or service (future)
- **Views:**
  - `POST /auth/password-reset/` — accepts email, generates token, sends email
  - `GET /auth/password-reset/confirm/<token>/` — validates token, shows password form
  - `POST /auth/password-reset/confirm/<token>/` — validates token, resets password
- **Token validation:**
  - Check token exists and not used
  - Check not expired (`expires_at > now()`)
  - Mark as used after successful reset
  - Invalidate token after use

**Security:**
- Token must be cryptographically random (use `secrets.token_hex()`)
- Single-use tokens (prevent replay)
- Time-limited (30 minutes expiry)
- Constant-time token comparison (prevent timing attacks)
- Rate limiting on password reset requests (future enhancement, not blocking for Iteration 1)

**Testing:**
- Unit tests for token generation, expiry logic
- Integration tests for password reset flow (email captured in test backend)
- Security tests for expired tokens, used tokens, invalid tokens

**Approval Status:** ✅ **APPROVED AS IMPLEMENTATION CHOICE**

**Justification:** This approach implements TASK-005 to TASK-008 as scoped, uses Django's standard email abstraction, and safely defers production email provider selection to deployment configuration (not an Iteration 1 blocker).

### DECISION 5: Content Model Database Schema

**Context:**
TASK-032 to TASK-045 require content model, ownership, lifecycle states, basic CRUD, version foundation. Requirements (Section 10) define content entity but leave exact schema to design. Phase 3.2 provides entity patterns.

**Requirements Analysis:**
- Section 10: Content entity supports title, topic, instructions, research refs, generated content, media, target platforms, reviews, validation, approval, schedule, publishing results, timestamps, ownership, lifecycle status
- Section 11: Lifecycle states (Draft → ... → Published)
- BR-001: User ownership required
- BR-007: Material edits invalidate approval
- Section 43: Version history required
- FR-003, FR-004: Create and edit content

**Iteration 1 Scope (TASK-032 to TASK-045):**
- Basic content model
- Ownership
- Lifecycle state foundation
- Version foundation (not full versioning system)
- CRUD operations

**Schema Design:**

**Content Model (Primary Entity):**
```
Table: content

Fields:
- id: Primary key (auto-increment integer or UUID)
- owner_id: Foreign key to auth_user (NOT NULL, indexed) — satisfies BR-001
- title: VARCHAR(255) (NOT NULL) — user-facing content name
- topic: VARCHAR(500) (NULL) — content topic/theme
- description: TEXT (NULL) — internal notes/instructions
- lifecycle_state: VARCHAR(50) (NOT NULL, default='draft') — current state
- current_version_id: Foreign key to content_version (NULL, self-referential via versions) — tracks active version
- created_at: TIMESTAMP (NOT NULL, default=now())
- updated_at: TIMESTAMP (NOT NULL, default=now(), auto-update)
- deleted_at: TIMESTAMP (NULL) — soft delete support

Indexes:
- owner_id (for ownership queries)
- lifecycle_state (for state filtering)
- created_at (for date range queries)

Constraints:
- lifecycle_state CHECK IN ('draft', 'in_progress', 'pending_review', 'approved', 'published', 'archived')
```

**ContentVersion Model (Version History Foundation):**
```
Table: content_version

Fields:
- id: Primary key (auto-increment integer or UUID)
- content_id: Foreign key to content (NOT NULL, indexed) — parent content
- version_number: INTEGER (NOT NULL) — 1, 2, 3, ... per content
- content_text: TEXT (NULL) — generated/edited content text
- created_by_id: Foreign key to auth_user (NOT NULL) — version author
- created_at: TIMESTAMP (NOT NULL, default=now())
- change_summary: TEXT (NULL) — what changed in this version
- is_approved: BOOLEAN (NOT NULL, default=False) — approval flag (simplified for Iteration 1)

Indexes:
- content_id, version_number (composite, unique) — enforce version uniqueness per content
- content_id, created_at (for version history queries)

Constraints:
- UNIQUE(content_id, version_number)
```

**Rationale:**
1. **Ownership:** `owner_id` on Content satisfies BR-001
2. **Lifecycle:** `lifecycle_state` enum supports workflow foundation (extensible to full state machine in later iterations)
3. **Versioning foundation:** ContentVersion table supports version history (BR-007, Section 43) without full approval/publishing integration (deferred to later iterations)
4. **Simplified for Iteration 1:** Full approval, review, publishing entities deferred (not in TASK-032 to TASK-045)
5. **Extensible:** Schema accommodates future additions (research FK, media FK, platform targets, etc.)

**Migration Strategy:**
- Iteration 1: Create `content` and `content_version` tables
- Content app: `content` Django app with `Content` and `ContentVersion` models
- Migrations: Forward-only, no modifications to auth migrations
- Database: Add-only migrations to development DB

**Future Extensions (Later Iterations):**
- Research FK (Iteration 2)
- AI generation FK (Iteration 3)
- Publishing job FK (Iteration 4)
- Campaign FK (Iteration 5)

**Approval Status:** ✅ **APPROVED AS IMPLEMENTATION CHOICE**

**Justification:** This schema satisfies TASK-032 to TASK-045 requirements, implements BR-001 (ownership), supports BR-007 (version history foundation), and aligns with Phase 3.2 entity patterns. It is scoped to Iteration 1 only (basic content + version foundation).

### DECISION 6: Test Framework

**Context:**
Iteration 0 deferred tests (no business logic). Iteration 1 introduces authentication, authorization, content CRUD — requires automated tests (FR-025, NFR-004). Phase 5.4 entry criteria require test framework selection.

**Requirements:**
- FR-025: Automated tests for critical business behavior
- NFR-004: Testability
- V1-AC-22: Critical workflow tests pass

**Options Evaluated:**

**Option A: Django's built-in test framework (unittest-based)**
- ✅ **Advantages:**
  - Zero additional dependencies
  - Standard Django pattern
  - `./manage.py test` command
  - Test database creation/teardown automatic
  - Django test client for views
  - ORM fixtures and factory support
- ❌ **Disadvantages:**
  - Verbose unittest syntax compared to pytest

**Option B: pytest + pytest-django**
- ✅ **Advantages:**
  - Modern test syntax (fixtures, parametrization)
  - Rich plugin ecosystem
  - Better test discovery
- ❌ **Disadvantages:**
  - Additional dependency (pytest, pytest-django)
  - Learning curve for Django developers familiar with unittest

**Option C: No test framework (manual testing only)**
- ❌ **Violates FR-025, NFR-004, V1-AC-22**

**Recommendation: Option A — Django's Built-In Test Framework**

**Rationale:**
1. **Zero dependencies:** Uses Django's standard `django.test.TestCase`
2. **Standard Django:** Official documentation, widely known pattern
3. **Sufficient for Iteration 1:** Unit tests, integration tests, view tests all supported
4. **Test database:** Django handles test database creation, migrations, teardown
5. **Test client:** `self.client.get()`, `self.client.post()` for view testing
6. **Requirements satisfied:** Supports FR-025 (automated tests), NFR-004 (testability)

**Implementation Approach:**

**Test Organization:**
```
content_automater/
  users/
    tests/
      __init__.py
      test_models.py       # UserProfile model tests
      test_views.py        # Auth view tests (login, logout, register)
      test_auth.py         # Authentication, authorization tests
      test_password_reset.py  # Password reset flow tests
  content/
    tests/
      __init__.py
      test_models.py       # Content, ContentVersion model tests
      test_views.py        # Content CRUD view tests
      test_ownership.py    # Authorization tests (cross-user access denied)
      test_lifecycle.py    # Lifecycle state transition tests
```

**Test Commands:**
- `./manage.py test` — Run all tests
- `./manage.py test users` — Run users app tests only
- `./manage.py test content` — Run content app tests only
- `./manage.py test users.tests.test_auth` — Run specific test module

**Test Database:**
- Django creates `test_ai_content_automater_dev` automatically
- Migrations applied before tests
- Database destroyed after tests
- Isolated from development database

**Test Categories for Iteration 1:**

1. **Model Tests:**
   - UserProfile creation, owner reference
   - Content creation with owner
   - ContentVersion creation, version numbering
   - Constraints (email uniqueness, lifecycle state enum, version uniqueness)

2. **Authentication Tests:**
   - Registration (valid, duplicate email, invalid email, weak password)
   - Login (valid credentials, invalid credentials)
   - Logout
   - Password hashing (never plaintext)
   - Session creation

3. **Authorization Tests:**
   - Login required (unauthenticated redirects)
   - Ownership enforcement (user A cannot access user B's content)
   - Administrator role checks (future)

4. **Password Reset Tests:**
   - Token generation, expiry, single-use
   - Invalid token rejection
   - Expired token rejection
   - Used token rejection
   - Password successfully reset

5. **Content CRUD Tests:**
   - Create content (owner assigned)
   - List content (only owner's content)
   - View content detail (owner only)
   - Edit content (owner only, unauthorized denied)
   - Delete content (owner only, unauthorized denied)

6. **Lifecycle Tests:**
   - State transitions (draft → in_progress → etc.)
   - Invalid transitions rejected

**Coverage Goals:**
- Model constraints: 100%
- Authentication logic: 100%
- Authorization checks: 100%
- Password reset: 100%
- Content CRUD: 100%
- Critical paths (registration, login, create content): 100%

**Test Execution:**
- Run tests before committing
- Tests must pass before code review
- CI/CD (future) runs tests automatically

**Approval Status:** ✅ **APPROVED AS IMPLEMENTATION CHOICE**

**Justification:** Django's built-in test framework is the standard approach, requires zero dependencies, and fully supports Iteration 1 testing requirements (FR-025, NFR-004, V1-AC-22).

### 3.1 EPIC-001: Identity & Access Management (TASK-001 to TASK-031)

**User Model (TASK-001):**
- Use Django's `auth.User` (already applied migrations)
- Create `users` app
- Create `UserProfile` model (OneToOne to User):
  - `user` (OneToOne to `auth.User`)
  - `role` (CharField: "user" or "administrator")
  - `created_at`, `updated_at`
- Migration: `users/migrations/0001_initial.py` (UserProfile only)

**Registration (TASK-002, TASK-003, TASK-004):**
- View: `RegistrationView` (FormView)
- Form: `RegistrationForm` (email, password1, password2, validation)
- Template: `users/templates/users/register.html`
- URL: `/auth/register/`
- Logic:
  - Validate email format, uniqueness
  - Validate password strength (Django's password validators)
  - Create `User` (email as username, password hashed)
  - Create `UserProfile` (role="user" by default)
  - Redirect to login on success
- Tests: `users/tests/test_views.py::TestRegistration`

**Password Reset (TASK-005 to TASK-008):**
- Model: `PasswordResetToken` (token, user FK, created_at, expires_at, used_at)
- Views:
  - `PasswordResetRequestView` (POST /auth/password-reset/)
  - `PasswordResetConfirmView` (GET/POST /auth/password-reset/confirm/<token>/)
- Email: Console backend (development), logged to console
- Token: 32-byte hex, expires in 30 minutes
- Tests: `users/tests/test_password_reset.py`

**Login/Logout (TASK-012 to TASK-019):**
- Views: Django's `LoginView`, `LogoutView` (built-in, customized templates)
- Templates: `users/templates/users/login.html`, logged-out confirmation
- URLs: `/auth/login/`, `/auth/logout/`
- Session: Django session middleware (already enabled in Iteration 0)
- CSRF: Enabled (Django default)
- Tests: `users/tests/test_auth.py::TestLogin`, `TestLogout`

**Authorization (TASK-020 to TASK-031):**
- Decorators: `@login_required` (Django built-in)
- Ownership checks: `content.owner == request.user` (in views)
- Role checks: `request.user.profile.role == "administrator"` (for admin features, minimal in Iteration 1)
- Middleware: No custom auth middleware needed (Django's `AuthenticationMiddleware` sufficient)
- Tests: `users/tests/test_auth.py::TestAuthorization`, `content/tests/test_ownership.py`

**Security (TASK-031):**
- CSRF protection: Enabled (Django default), tokens in forms
- Password hashing: Django's default (PBKDF2)
- Session security:
  - `SESSION_COOKIE_HTTPONLY = True` (base.py)
  - `SESSION_COOKIE_SECURE = True` (production.py only)
  - `SESSION_COOKIE_SAMESITE = 'Lax'` (base.py)
- Session timeout: `SESSION_COOKIE_AGE = 1209600` (2 weeks, base.py)

- Tests: `content/tests/test_models.py::TestContent`, `TestContentVersion`

**Content CRUD (TASK-034, TASK-036 to TASK-038):**

## 8. SECURITY CONTROLS

### 8.1 Authentication Security

- Password hashing: Django's PBKDF2 (260,000 iterations, SHA256)
- Password validators:
  - `MinimumLengthValidator` (min length 8)
  - `CommonPasswordValidator` (reject common passwords)
  - `NumericPasswordValidator` (not all numeric)
- Session security:
  - `SESSION_COOKIE_HTTPONLY = True` (prevent XSS access)
  - `SESSION_COOKIE_SECURE = True` (production only, HTTPS)
  - `SESSION_COOKIE_SAMESITE = 'Lax'` (CSRF mitigation)
  - `SESSION_COOKIE_AGE = 1209600` (2 weeks)
- CSRF protection: Enabled (Django default), tokens in all forms

### 8.2 Authorization Security

- Login required: `@login_required` decorator on all protected views
- Ownership checks: `content.owner == request.user` before access
- Query filtering: `Content.objects.filter(owner=request.user)` (never query all content)
- Permission checks: Role-based checks where needed (`request.user.profile.role`)

### 8.3 Password Reset Security

- Token: Cryptographically random (32 bytes hex, `secrets.token_hex()`)
- Expiry: 30 minutes
- Single-use: Mark as used after successful reset
- Constant-time comparison: Prevent timing attacks
- Rate limiting: Future enhancement (not Iteration 1 blocker)

### 8.4 Input Validation

- Django forms: Server-side validation (email, password, required fields)
- Model constraints: Database-level (unique email, lifecycle state enum, etc.)
- CSRF tokens: Required for POST/PUT/DELETE
- XSS protection: Django template autoescaping enabled

## 9. ERROR HANDLING AND LOGGING

### 9.1 Error Handling

- Authentication errors: Clear user-facing messages (invalid email/password)
- Authorization errors: HTTP 403 Forbidden (not 404, to prevent info disclosure)
- Validation errors: Form errors displayed inline
- Server errors: HTTP 500, logged, generic user message (no stack traces)
- Database errors: Catch integrity errors (duplicate email, etc.), user-friendly message

### 9.2 Logging

**Development Logging:**
- Console output (Django default)
- DEBUG=True: Full stack traces
- Email backend: Console (password reset emails logged to console)

**Production Logging (future):**
- Structured logs (JSON)
- Log levels: ERROR, WARNING, INFO
- Security events: Failed login, password reset, authorization failures
- No passwords, tokens, or secrets in logs

**Iteration 1 Logging:**
- Minimal logging (Django defaults)
- Console output only
- No Sentry or external logging (deferred)
