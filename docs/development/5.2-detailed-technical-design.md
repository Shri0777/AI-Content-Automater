### DECISION-TD-003: Settings Organization

**Status:** ✅ RECOMMENDED

**Selected:** Split settings with environment-based selection

**Structure:**
```
content_automater/settings/
├── __init__.py            # Import active settings
├── base.py                # Common settings
├── development.py         # Dev overrides
└── production.py          # Production config
```

**Settings Module Selection:**
```python
# Via environment variable
DJANGO_SETTINGS_MODULE=content_automater.settings.development
```

**Rationale:**
- Django best practice for production readiness
- Clear separation: development conveniences vs production security
- Avoids single-file conditional complexity
- Scales well for staging/production variations
- Standard pattern in Django community

**Alternative Rejected:** Single file with environment variables
- Reason: Less clear dev/prod separation, all logic in one file

### DECISION-TD-005: Secret Management

**Status:** ✅ RECOMMENDED

**Strategy:** Environment variables via `.env` file (development) / system environment (production)

**Secret Key Management:**
1. **Generation:** Developer generates once using Django utility
2. **Storage:** `.env` file (development), AWS Secrets Manager (production - later)
3. **Git Exclusion:** `.env` in `.gitignore`, `.env.example` committed
4. **No Defaults:** Production settings MUST fail if SECRET_KEY missing

**Environment Variables:**
```bash
# .env.example (committed)
SECRET_KEY=<generate-with-django-command>
DEBUG=True
ALLOWED_HOSTS=localhost,127.0.0.1
DB_NAME=ai_content_automater_dev
DB_USER=postgres
DB_PASSWORD=<your-local-password>
DB_HOST=localhost
DB_PORT=5432
```

**Security Requirements:**
- Real `.env` excluded from Git (via `.gitignore`)
- `.env.example` contains placeholders only
- No secrets in source code
- Production must explicitly set all secrets
- Missing secrets cause immediate startup failure

**Environment Loading:**
- Use `python-dotenv` for `.env` file parsing
- Load in `settings/base.py` before Django settings

## 8. SECURITY BASELINE

### 8.1 Foundation Security Requirements

**Mandatory for Iteration 0:**

1. **Secret Key Protection**
   - Never committed to Git
   - Loaded from environment only
   - Production fails without explicit value
   - Development requires manual generation

2. **DEBUG Configuration**
   - `DEBUG=True` for development (explicit)
   - `DEBUG=False` for production (must be explicit)
   - Production must never default to True

3. **Allowed Hosts**
   - Development: `localhost`, `127.0.0.1`
   - Production: Must be explicitly configured (no wildcard)

4. **Database Credentials**
   - Never hardcoded
   - Loaded from environment
   - `.env` excluded from Git

5. **Git Exclusion**
   ```gitignore
   # Python
   __pycache__/
   *.py[cod]
   *$py.class

   # Virtual Environment
   venv/
   env/
   ENV/

   # Django
   *.log
   db.sqlite3
   /static/
   /media/

   # Environment
   .env

   # IDE
   .vscode/
   .idea/
   *.swp
   ```

6. **Error Handling**
   - No stack traces with secrets
   - Safe error messages in production
   - Logging configured to filter credentials

### 8.2 Security Controls NOT in Iteration 0

**Deferred to Later Iterations:**
- User authentication (Iteration 1)
- Authorization middleware (Iteration 1)
- CSRF protection (enabled by default, verified in Iteration 1)
- Session security (configured in Iteration 1)
- API authentication (Iteration 2+)
- Rate limiting (later)
- Input validation (with feature implementation)
- Content Security Policy (production hardening)

**Justification:** Foundation establishes secure configuration patterns, but authentication/authorization require business logic (Iteration 1+)

## 15. FAILURE HANDLING AND RECOVERY

### 15.1 Common Setup Failures

**F-001: Django Import Error**
- **Symptom:** `ModuleNotFoundError: No module named 'django'`
- **Cause:** Virtual environment not activated or dependencies not installed
- **Resolution:** `source venv/bin/activate && pip install -r requirements/development.txt`

**F-002: SECRET_KEY Missing**
- **Symptom:** `ImproperlyConfigured: The SECRET_KEY setting must not be empty`
- **Cause:** `.env` file missing or SECRET_KEY not set
- **Resolution:** Create `.env`, generate secret key, add to file

**F-003: Database Connection Refused**
- **Symptom:** `could not connect to server: Connection refused`
- **Cause:** PostgreSQL service not running
- **Resolution:** `sudo systemctl start postgresql`

**F-004: Database Does Not Exist**
- **Symptom:** `FATAL: database "ai_content_automater_dev" does not exist`
- **Cause:** Database not created
- **Resolution:** `sudo -u postgres createdb ai_content_automater_dev`

**F-005: Authentication Failed**
- **Symptom:** `FATAL: password authentication failed for user "postgres"`
- **Cause:** Incorrect database credentials in `.env`
- **Resolution:** Update DB_PASSWORD in `.env` with correct password

**F-006: Migration Errors**
- **Symptom:** `django.db.utils.ProgrammingError` during migrate
- **Cause:** Database state inconsistent
- **Resolution:** Drop database, recreate, re-run migrations (safe in Iteration 0)

**F-007: Port 8000 Already in Use**
- **Symptom:** `Error: That port is already in use`
- **Cause:** Another process using port 8000
- **Resolution:** `python manage.py runserver 8001` (use different port)

**F-008: Python Version Incompatibility**
- **Symptom:** Django installation fails or import errors
- **Cause:** Python 3.14 incompatible with Django 5.1
- **Resolution:** Use Python 3.13 via pyenv, update design document

### 15.2 Recovery Procedures

**Complete Reset (Safe in Iteration 0):**
```bash
# 1. Deactivate and remove virtual environment
deactivate
rm -rf venv/

# 2. Remove Django files
rm -rf content_automater/
rm manage.py

# 3. Drop and recreate database
sudo -u postgres dropdb ai_content_automater_dev
sudo -u postgres createdb ai_content_automater_dev

# 4. Start fresh from STEP 2 of implementation sequence
```

**Partial Reset (Keep dependencies):**
```bash
# 1. Drop database
sudo -u postgres dropdb ai_content_automater_dev
sudo -u postgres createdb ai_content_automater_dev

# 2. Delete migrations (if custom ones exist)
# (None exist in Iteration 0)

# 3. Re-run migrations
python manage.py migrate
```

## 17. RISKS AND TRADE-OFFS

### 17.1 Technical Risks

**R-TD-001: Python 3.14 Compatibility**
- **Risk:** Django 5.1 not officially tested with Python 3.14
- **Likelihood:** Medium
- **Impact:** Medium (blocks setup)
- **Mitigation:** Verify during implementation, use Python 3.13 if needed
- **Detection:** Django installation or import errors

**R-TD-002: PostgreSQL Authentication**
- **Risk:** Local PostgreSQL credentials unknown or misconfigured
- **Likelihood:** Low (service verified running)
- **Impact:** Low (easily fixed)
- **Mitigation:** Document credential setup in README
- **Detection:** Connection refused errors

**R-TD-003: Virtual Environment Issues**
- **Risk:** User unfamiliar with venv/virtualenv
- **Likelihood:** Low (standard Python practice)
- **Impact:** Low (documentation resolves)
- **Mitigation:** Clear README instructions
- **Detection:** Import errors or pip issues

### 17.2 Design Trade-Offs

**Trade-Off 1: Split Settings vs Single File**
- **Chosen:** Split settings
- **Trade-off:** More files vs clearer separation
- **Rationale:** Production readiness outweighs simplicity
- **Reversal:** Merge into single file (medium effort)

**Trade-Off 2: PostgreSQL vs SQLite**
- **Chosen:** PostgreSQL from start
- **Trade-off:** Setup complexity vs production parity
- **Rationale:** Service already running, no additional cost
- **Reversal:** Switch to SQLite (low effort in Iteration 0)

**Trade-Off 3: No Business Apps vs Empty Apps**
- **Chosen:** No apps in Iteration 0
- **Trade-off:** Minimal structure vs future-ready folders
- **Rationale:** Apps should contain code, not be placeholders
- **Reversal:** None needed (apps created when needed)
