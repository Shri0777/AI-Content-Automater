# Phase 6 Audit and Repair Report

## 1. Executive Summary & Audit Preflight

An exhaustive architectural, security, concurrency, and API audit of Phase 6 (Buffer Social Publishing & Scheduling) was conducted against official Buffer API documentation, production concurrency invariants, idempotency guarantees, and data integrity requirements.

While preliminary implementations passed basic tests using legacy REST endpoints, the audit uncovered multiple verified architectural, concurrency, security, and state-machine defects. All defects have been repaired, verified, and documented below.

---

## 2. Verified Defects, Severity & Root Cause Analysis

### Defect 1: Deprecated Legacy REST API Contract (Severity: High)
- **Root Cause**: The initial implementation targeted Buffer REST API v1 (`https://api.bufferapp.com/1/`, `/1/user.json`, `/1/profiles.json`, `/1/updates/create.json`). Official Buffer documentation indicates the legacy REST API is deprecated, closed to new app registrations, and replaced by the unified GraphQL API.
- **Files Changed**:
  - [`content_automater/settings/base.py`](file:///home/shri/Development/AI-AUTOMATER/content_automater/settings/base.py): Updated canonical `BUFFER_API_URL` to `https://api.buffer.com`.
  - [`.env.example`](file:///home/shri/Development/AI-AUTOMATER/.env.example): Added `BUFFER_API_URL`.
  - [`content/services/buffer_service.py`](file:///home/shri/Development/AI-AUTOMATER/content/services/buffer_service.py): Migrated client to official GraphQL queries (`GetAccountAndOrgs`, `GetChannels`) and mutations (`createPost`).
- **API Documentation Consulted**: [Buffer Developers Portal](https://developers.buffer.com), [Quick Start](https://developers.buffer.com/docs/quick-start), [REST to GraphQL Migration](https://developers.buffer.com/docs/rest-api-migration).

### Defect 2: Premature `published_at` Timestamp for Scheduled Posts (Severity: High)
- **Root Cause**: In `BufferPublishingOrchestrator.execute_publishing`, `publication.published_at = timezone.now()` was unconditionally set for all successful responses, including scheduled posts.
- **Impact**: Database records for scheduled posts claimed `status='scheduled'` while simultaneously asserting `published_at` was already recorded.
- **Files Changed**:
  - [`content/services/publishing_orchestrator.py`](file:///home/shri/Development/AI-AUTOMATER/content/services/publishing_orchestrator.py): Separated timestamp assignment: when scheduled, `scheduled_at` is set and `published_at = None`; when immediate, `published_at = timezone.now()` and `scheduled_at = None`.
  - [`content/templates/content/detail.html`](file:///home/shri/Development/AI-AUTOMATER/content/templates/content/detail.html): Accurately displays Target Schedule vs Published At.

### Defect 3: Concurrency Race Condition in Idempotency & Dispatch (Severity: High)
- **Root Cause**: `execute_publishing` performed a non-atomic `filter().first()` check on `idempotency_key` outside of a row-level database lock.
- **Impact**: Concurrent requests with the same idempotency key or rapid double-submissions could both pass the existence check before either saved a `publishing` record, leading to duplicate posts dispatched to Buffer.
- **Files Changed**:
  - [`content/services/publishing_orchestrator.py`](file:///home/shri/Development/AI-AUTOMATER/content/services/publishing_orchestrator.py): Wrapped preflight in `transaction.atomic()` with `select_for_update()` on the `Content` record. Added `IntegrityError` handling on the unique constraint to gracefully prevent duplicates.

### Defect 4: Missing `ambiguous` State in Duplicate Prevention (Severity: High)
- **Root Cause**: The duplicate check in `publishing_orchestrator.py` only checked `('published', 'scheduled', 'publishing')`, omitting `'ambiguous'`.
- **Impact**: If a request timed out after submission (entering `ambiguous` state per BR-018), a subsequent publish attempt would re-dispatch to Buffer, violating BR-018's prohibition against blind retries.
- **Files Changed**:
  - [`content/services/publishing_orchestrator.py`](file:///home/shri/Development/AI-AUTOMATER/content/services/publishing_orchestrator.py): Included `'ambiguous'` in duplicate prevention: `('published', 'scheduled', 'publishing', 'ambiguous')`.

### Defect 5: Unvalidated Target Social Channels (Severity: Medium-High)
- **Root Cause**: User-supplied `profile_ids` from the HTTP POST payload were accepted without validating whether those IDs belonged to the authorized channels returned by Buffer.
- **Impact**: A user could attempt to publish to unauthorized or arbitrary channel IDs.
- **Files Changed**:
  - [`content/services/publishing_orchestrator.py`](file:///home/shri/Development/AI-AUTOMATER/content/services/publishing_orchestrator.py): Validated requested channel IDs against `buffer_service.get_profiles()`, rejecting unauthorized destinations.

### Defect 6: Unrestricted Reconciliation Gate (Severity: Medium)
- **Root Cause**: `BufferPublishingOrchestrator.reconcile_publication()` permitted reconciliation of any publication record, regardless of whether its status was `ambiguous`.
- **Impact**: Any publication (e.g. `published` or `failed`) could be arbitrarily changed by the owner.
- **Files Changed**:
  - [`content/services/publishing_orchestrator.py`](file:///home/shri/Development/AI-AUTOMATER/content/services/publishing_orchestrator.py): Added explicit guard: `if publication.status != 'ambiguous': return {'success': False, 'error': ...}`.

### Defect 7: Inaccurate Partial Success Messaging (Severity: Medium)
- **Root Cause**: When publishing to multiple channels, if channel 1 succeeded and channel 2 failed, `overall_success` was `False`, and `views.py` flashed `messages.error(request, "Publishing failed")`.
- **Impact**: Users were told the entire publication failed even though content had already been published to channel 1, prompting duplicate submissions.
- **Files Changed**:
  - [`content/services/publishing_orchestrator.py`](file:///home/shri/Development/AI-AUTOMATER/content/services/publishing_orchestrator.py): Added `partial_success` tracking.
  - [`content/views.py`](file:///home/shri/Development/AI-AUTOMATER/content/views.py): Flashed `messages.warning` detailing partial success (e.g., 1/2 destinations succeeded).

### Defect 8: Insufficient Lead Time for Scheduled Publications (Severity: Medium)
- **Root Cause**: Scheduled time only checked `scheduled_at <= now + 60s`.
- **Impact**: 60 seconds is insufficient for social scheduling APIs due to clock drift and queue latency, leading to upstream schedule rejection.
- **Files Changed**:
  - [`content/services/publishing_orchestrator.py`](file:///home/shri/Development/AI-AUTOMATER/content/services/publishing_orchestrator.py): Enforced a minimum lead time of at least 5 minutes in the future, with strict ISO 8601 UTC timestamp formatting for GraphQL `dueAt`.

### Defect 9: Unfiltered External Response Body Storage (Severity: Low-Medium)
- **Root Cause**: `publication.response_data` persisted raw, unstructured API response dictionaries.
- **Impact**: Potential leakage of unnecessary internal provider metadata into database storage.
- **Files Changed**:
  - [`content/services/buffer_service.py`](file:///home/shri/Development/AI-AUTOMATER/content/services/buffer_service.py), [`content/services/publishing_orchestrator.py`](file:///home/shri/Development/AI-AUTOMATER/content/services/publishing_orchestrator.py): Sanitized response dictionaries to persist only essential audit attributes (`post_id`, `status`, `channel_id`, `mode`).

## 5. Remaining Risks & Live Integration Limitations

1. **Mocked Testing Limitation**: Automated tests use 100% mocked HTTP responses. Live API integration requires active Buffer API credentials (`BUFFER_ACCESS_TOKEN`) and connected social channels. Production readiness should not be claimed solely based on mocked tests until verified with live credentials.
2. **Channel-Specific Permissions**: While `isQueuePaused` and basic channel types are validated, certain platforms (e.g. Instagram Reels or Pinterest Boards) require specific media assets or scopes not applicable to text publishing.
3. **Local Idempotency Boundary**: Local idempotency protects the local application from double-submitting to Buffer, but exactly-once delivery guarantees across network boundaries depend on Buffer's external receipt.

## 7. Direct Repair Pass (2026-10-21)

The following defects were repaired in the working tree:

- Buffer channel discovery now distinguishes an empty channel list from failed/invalid discovery and raises on discovery failure. Publishing fails closed when destination authorization cannot be verified. The content detail page degrades gracefully when Buffer is unavailable.
- Buffer `createPost` mutations are no longer blindly retried after HTTP 5xx or connection failures. Those outcomes are recorded as ambiguous for manual reconciliation. A successful immediate mutation is recorded as `pending` unless Buffer explicitly reports a sent/published state; `published_at` is not set merely because Buffer accepted the mutation. Pending records are included in duplicate prevention.
- Environment provider auto-detection no longer silently chooses OpenAI when the key is ambiguous. Unknown capability names return no providers instead of mapping to image generation.
- Production requires a stable credential-encryption key and enables secure-cookie/content-type/frame/referrer defaults. The example environment file documents stable key generation. Existing credentials must be migrated/re-encrypted before changing a key.
- GNews request exceptions no longer log or return exception text that may contain the API key in its query URL.
- RSS fetching now uses bounded requests, validates each redirect target, disables automatic redirect following, and caps the response at 2 MiB. URL validation blocks non-global IP destinations and IPv6 private/reserved destinations. DNS rebinding at the socket-connection layer is still a residual risk; a fully pinned egress transport or outbound network policy is required to eliminate it completely.
- Provider configuration validation is POST-only, its dashboard action now submits POST with CSRF protection, and provider API requests do not follow redirects to a potentially different host.
- Research execution serializes duplicate submissions, records completion/error metadata, and explicitly reports selected source categories that do not yet have active connectors. Current research implementation still actively searches news sources only; other profile categories are not falsely represented as searched.
- Updated tests to encode the safer publishing semantics and safe RSS fetch boundary.
