## 2. Credential protection proposal

**Recommended implementation:** store provider API keys encrypted at application level using an established authenticated-encryption implementation, with the encryption key provided separately through deployment secret management. Do not invent a cryptographic primitive, commit a key, store plaintext keys, or derive the encryption key from a database value. Do not assume Django `SECRET_KEY` is an approved credential-encryption key.

- The encryption key must be absent from source control and the database, supplied at runtime, and required only by code paths that need to encrypt/decrypt provider credentials.
- Fail closed if the key is missing or decryption fails. Do not fall back to plaintext.
- Keep the ciphertext format versioned so key rotation can be designed and tested.
- Credential write endpoints accept the secret; read/list endpoints return only safe metadata and a boolean/configured status. Never return the stored key, even masked suffixes unless specifically justified.
- Exclude credentials and authorization headers from application logs, exception messages, tracing, audit metadata, and test snapshots.
- Unit tests use fake keys and fake credentials. Real provider credentials must not be requested or created for this iteration's local tests.

**Gate:** choose and document the concrete library, key name, deployment injection path, rotation procedure, and production secret-management service before merging credential-storage code. These details are proposals, not claims about existing infrastructure.

## 3. RSS/Atom retrieval security proposal

RSS feed URLs are user-influenced outbound network requests and must be treated as an SSRF boundary. Prefer a controlled allowlist of configured feed domains if product UX permits it. If arbitrary feed URLs are required, the implementation must:

1. Permit only `https` by default; any `http` exception must be explicit and documented.
2. Reject credentials in URLs, nonstandard ports unless allowlisted, IP-literal destinations, loopback/private/link-local/multicast/reserved/metadata-service addresses, and unsupported schemes.
3. Resolve and validate destinations at connection time; validate every redirect target and cap redirect count. Do not rely on hostname string checks or a denylist alone.
4. Defend against DNS rebinding/time-of-check-time-of-use gaps as far as the selected HTTP client and network architecture allow; enforce egress restrictions at deployment where available.
5. Apply connect/read/total timeouts, maximum response bytes, maximum feed items, maximum text lengths, and bounded parsing work.
6. Parse XML with external entity/DTD processing disabled. Never execute embedded HTML/script. Sanitize display output and use safe external-link behavior.
7. Store fetch status and a sanitized error category; do not expose internal IPs, stack traces, or sensitive network details to users.

GNews requests must use a fixed provider endpoint in the adapter, HTTPS, strict response/time limits, and an API key supplied only by the credential service. Do not accept a user-supplied base URL for the GNews adapter.

## 4. Query execution and API proposal

**Initial implementation proposal:** use a synchronous request only if explicit connect/read/total timeouts and bounded result limits keep it inside the application's request budget. Otherwise use the project's approved background-job system, if one is configured. Do not add Redis/Celery solely by assumption. Persist a query record before outbound execution, and persist sanitized success/failure state after it finishes.

Minimum query states: `pending`, `running`, `succeeded`, `partial`, `failed`. A synchronous-only first implementation may omit `pending`/`running` from user-visible responses only if the service still records accurate state transitions. A multi-provider query must preserve successful results when another adapter fails.

Proposed endpoint contract (finalize against existing URL conventions before implementation):
- `GET /api/research-providers`: available adapter codes and the user's connection status, never credentials.
- `POST /api/research-providers/connections`: create/update a connection for RSS/Atom feed configuration or GNews API credentials.
- `GET /api/research-providers/connections`: safe metadata for current user's connections only.
- `POST /api/research-providers/connections/{id}/validate`: validate a connection and return a safe status/error code.
- `DELETE /api/research-providers/connections/{id}`: delete an owned connection.
- `POST /api/research/queries`: validate query and selected owned connections, persist the query, execute bounded provider calls, normalize and persist results.
- `GET /api/research/queries/{id}` and `GET /api/research/queries/{id}/results`: owner-scoped status and paginated results.
- `POST /api/research/queries/{id}/refine`: create a child query; preserve the original query/results unchanged.

Every endpoint must use authentication and owner-scoped querysets. Cross-user IDs should produce a consistent not-found response. Define serializer validation, status codes, error categories, maximum query length, maximum providers/query, result limit, pagination, request idempotency, and rate limits before coding.

## 5. Result retention and provider terms

Persist only fields needed for research workflow and attribution: title, short snippet if permitted, canonical URL, publisher/source, provider identifier, published/retrieved timestamps, rank, and bounded safe metadata. Avoid persisting full article bodies by default even though a provider plan may return them. A GNews paid plan does not grant rights to publisher-owned article text or images. Do not publish or regenerate long article text based solely on search-result access.

Because GNews's published terms state commercial-use permission ends when an active paid subscription ends, including for previously stored/cached data, design a provider data-usage policy before commercial activation. It must define what stored data is retained, disabled, or deleted if the plan lapses. RSS feeds also require feed-by-feed rights/terms review.

## 6. Version immutability and approval-state resolution proposal

Do not use a blanket database trigger that rejects every update to a row containing mutable `is_approved` state. Proposed separation:
- Immutable `ContentVersion` snapshot fields: content FK, version number, immutable content payload/snapshot, creator, created timestamp, and snapshot hash.
- Mutable approval record/state: separate `ContentVersionApproval` record (or equivalent immutable approval events) tied to a specific version, with approver, decision, timestamp, and optional reason. If revocation/re-approval is required, append events rather than rewriting the snapshot.
- Database immutability enforcement should reject updates/deletes to snapshot content while allowing only the separately modelled approval operation. Test the behavior against PostgreSQL and confirm migration/backfill semantics before implementing triggers.

This is an engineering proposal. Inspect existing model/view/test contracts and determine whether the current `is_approved` field has already been used in persisted data before choosing the migration. Never drop/recreate the existing test database to make this migration easier.

## 7. TASK-046 lifecycle API resolution proposal

The task register's JSON API contract is distinct from the existing server-rendered redirecting view. Preserve the UI route. Add a JSON endpoint only after confirming the project's API convention, with a shared transition service so both routes enforce the same ownership and transition rules.

Proposed contract: `POST /api/content/{id}/transition` with JSON `{ "target_state": "..." }`; success returns the updated content state and identifier. Invalid payload/state transition returns 400 or 422 per the chosen project convention; unauthenticated returns 401; missing or non-owned content returns 404; unexpected failure returns a safe 500 response with correlation ID. The final choice of 400 versus 422 and response schema must be consistent with the rest of the API and documented before implementation. Add tests for every supported transition and cross-owner denial.
