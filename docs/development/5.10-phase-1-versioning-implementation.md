### ✅ TASK-050: Database-Level Immutability Enforcement

**Status:** Implemented — Option A (Selective Trigger)  
**Decision Date:** 2026-10-14 22:25  
**Implementation Date:** 2026-10-14 23:00

**User-Approved Approach:**
- Selective PostgreSQL trigger that checks which fields are being modified
- Blocks updates to immutable snapshot fields
- Allows updates to mutable approval metadata (`is_approved`)

**Implementation Details:**

**Migration:** `content/migrations/0002_version_immutability.py`

```python
CREATE OR REPLACE FUNCTION prevent_content_version_snapshot_update()
RETURNS TRIGGER AS $$
BEGIN
    -- Check if any immutable snapshot field is being changed
    IF (OLD.content_id IS DISTINCT FROM NEW.content_id) OR
       (OLD.version_number IS DISTINCT FROM NEW.version_number) OR
       (OLD.content_text IS DISTINCT FROM NEW.content_text) OR
       (OLD.created_by_id IS DISTINCT FROM NEW.created_by_id) OR
       (OLD.created_at IS DISTINCT FROM NEW.created_at) OR
       (OLD.change_summary IS DISTINCT FROM NEW.change_summary) THEN
        
        RAISE EXCEPTION 'Content version snapshot fields are immutable';
    END IF;
    
    -- Allow the update if only mutable fields changed (is_approved)
    RETURN NEW;
END;
$$ LANGUAGE plpgsql;

CREATE TRIGGER prevent_version_snapshot_update
BEFORE UPDATE ON content_version
FOR EACH ROW EXECUTE FUNCTION prevent_content_version_snapshot_update();
```

**Field Classification:**

| Field | Status | Reason |
|-------|--------|--------|
| `content_id` | **IMMUTABLE** | Version belongs to specific content |
| `version_number` | **IMMUTABLE** | Version sequence is fixed |
| `content_text` | **IMMUTABLE** | Content snapshot integrity |
| `created_by_id` | **IMMUTABLE** | Historical record of creator |
| `created_at` | **IMMUTABLE** | Audit trail timestamp |
| `change_summary` | **IMMUTABLE** | Historical change description |
| `is_approved` | **MUTABLE** | Approval workflow metadata |

**Verification:**
- ✅ Migration applied successfully to test database
- ✅ Trigger function created without errors
- ✅ Rollback SQL included for reversibility
- ✅ No impact on existing data

**Why Option A:**
1. **Surgical precision:** Only blocks what needs to be blocked
2. **Workflow compatibility:** Approval process works without workarounds
3. **Clear error messages:** Trigger provides explicit feedback
4. **Maintainability:** Easy to understand which fields are protected
5. **Safety:** No application-level bypasses possible

```python
def get_status_info(self):
    """Return comprehensive status information."""
    return {
        'lifecycle_state': self.lifecycle_state,
        'lifecycle_state_display': self.get_lifecycle_state_display(),
        'current_version_number': self.current_version.version_number if self.current_version else None,
        'version_count': self.versions.all().count(),
        'last_state_change_at': self.updated_at,
        'available_transitions': self._get_available_transitions(),
        'created_at': self.created_at,
        'updated_at': self.updated_at,
    }

def _get_available_transitions(self):
    """Return list of valid next states."""
    valid_transitions = {
        'draft': ['in_progress'],
        'in_progress': ['pending_review', 'draft'],
        'pending_review': ['approved', 'draft'],
        'approved': ['published'],
        'published': ['archived'],
        'archived': [],
    }
    return valid_transitions.get(self.lifecycle_state, [])
```

## 🔴 BLOCKED TASK: TASK-050 — Database Immutability Trigger

**Design Document Specification:**
```sql
CREATE OR REPLACE FUNCTION prevent_version_update()
RETURNS TRIGGER AS $$
BEGIN
    RAISE EXCEPTION 'content_version rows are immutable and cannot be updated';
END;
$$ LANGUAGE plpgsql;

CREATE TRIGGER prevent_version_update
BEFORE UPDATE ON content_version
FOR EACH ROW EXECUTE FUNCTION prevent_version_update();
```

**Blocker Identified:** Design conflict with implementation requirements

### Problem

The design specifies a **blanket UPDATE trigger** that prevents ALL updates to `content_version`, but:

1. **The model contains `is_approved` field** which is approval metadata, not content snapshot
2. **User instructions explicitly state:** "Do not introduce a blanket database trigger that blocks legitimate approval-state updates. Snapshot immutability must not prevent approval metadata or audit events from changing through authorized operations."

### Current Model Structure

```python
class ContentVersion(models.Model):
    # Immutable snapshot fields:
    content = models.ForeignKey(Content, ...)
    version_number = models.IntegerField()
    content_text = models.TextField(...)      # IMMUTABLE
    created_by = models.ForeignKey(User, ...)
    created_at = models.DateTimeField(...)
    change_summary = models.TextField(...)     # IMMUTABLE
    
    # Mutable approval metadata:
    is_approved = models.BooleanField(default=False)  # MAY NEED UPDATES
```

### Resolution Options

**Option A: Selective Trigger (Recommended)**
```sql
CREATE OR REPLACE FUNCTION prevent_content_snapshot_update()
RETURNS TRIGGER AS $$
BEGIN
    -- Allow is_approved updates only
    IF OLD.content_id <> NEW.content_id OR
       OLD.version_number <> NEW.version_number OR
       OLD.content_text <> NEW.content_text OR
       OLD.created_by_id <> NEW.created_by_id OR
       OLD.created_at <> NEW.created_at OR
       OLD.change_summary <> NEW.change_summary THEN
        RAISE EXCEPTION 'Content snapshot fields are immutable';
    END IF;
    RETURN NEW;
END;
$$ LANGUAGE plpgsql;
```

**Option B: Separate Approval Table**
- Remove `is_approved` from ContentVersion
- Create `ContentApproval` table with FK to ContentVersion
- Trigger blocks ALL ContentVersion updates
- Approval state lives separately

**Option C: Application-Level Only**
- No database trigger
- Rely on application code (no update methods exist)
- Document immutability contract in model docstring
- Add application-level tests

### Current Safety Measures

Even without trigger, immutability is partially enforced:

1. ✅ No `update_version()` or similar methods exist in model
2. ✅ All version creation uses `create_initial_version()` or `create_next_version()`
3. ✅ No views modify existing versions
4. ✅ Authorization prevents cross-user access

**Remaining Risk:** Django ORM allows direct `ContentVersion.objects.filter(...).update()` bypass

### Recommendation

**Implement Option A** (selective trigger) with explicit allow-list for `is_approved`:
- Protects snapshot integrity (content_text, version_number, etc.)
- Permits approval workflow updates
- Aligns with user requirements
- Can be extended if other metadata fields need mutability

**Required for implementation:**
- User approval of Option A
- Confirmation that `is_approved` needs to be updateable
- OR decision to proceed with Option B or C
