# Phase 5.9C — Resume-Focused Scope Trim

**Date:** 2026-10-14  
**Status:** Proposed scope baseline; not yet merged into the authoritative requirements  
**Purpose:** Preserve production-quality engineering while reducing low-value breadth and avoiding unnecessary paid services.  
**Authority:** `docs/Requirements/REQUIREMENTS.MD` remains authoritative until explicit change control updates it.

## 1. Product target

Build AI Content Automater V2 as a complete, credible, production-oriented portfolio application. Public production deployment and paid service activation are optional later milestones. Engineering quality is not optional: security, authorization, correctness, maintainability, automated tests, observable failures, and reproducible setup apply from the beginning.

Optimize for one dependable end-to-end workflow rather than many partially implemented features.

## 2. Core workflow to demonstrate

1. A user configures a topic, audience, geography/language where relevant, platforms, content goals, and research preferences.
2. The research engine discovers material from RSS/Atom and GNews; filters by topic, date, relevance, and user constraints; canonicalizes URLs; deduplicates stories; and records source metadata.
3. Research results are ranked and presented with source links, publication/retrieval times, concise evidence summaries, and transparent limitations. Credibility and corroboration signals must be explainable; the system must not pretend to verify facts it cannot verify.
4. The user selects or excludes sources and can inspect why a result is relevant. The generation service receives selected evidence and attribution metadata, not a blind dump of every retrieved result.
5. The AI generates original, platform-appropriate content grounded in the selected evidence, then performs two review stages, bounded correction, and deterministic platform/content validation.
6. A user explicitly approves a specific content version; material edits invalidate that approval.
7. The user schedules or immediately publishes approved content to the supported platform set.
8. Each platform attempt has an accurate independent outcome, safe bounded retries, and useful error details. The user can inspect research provenance, content/version history, and publishing outcomes.

Research is a first-class product capability, not a disposable pre-processing step. The quality goal is relevant, timely, attributable, sufficiently corroborated evidence and original content—not maximum article volume. Never fabricate sources, dates, quotes, corroboration, or confidence. Distinguish source-reported facts, model inference, and unresolved claims. No workflow may bypass authorization, review, validation, approval, or publishing safeguards.

## 3. Keep in the first demonstrable release

### Product capabilities
- Authentication, user ownership, and authorization checks.
- Content CRUD, manual editing, and immutable content snapshots with separate approval records/events.
- One complete research path: RSS/Atom feeds plus the selected GNews adapter, behind a small provider interface. Keep adapters independently testable with mocked responses.
- AI generation and two-stage review with bounded correction. Make retry/revision limits configurable and finite; never add autonomous unbounded loops.
- Explicit approval, deterministic validation, and approval invalidation after material edits.
- Scheduling with timezone correctness and a minimal recurring-campaign implementation only if the shared scheduler supports it safely.
- Direct publishing to a deliberately small initial platform set. Prefer one fully verified platform integration as the vertical slice; add another only when its authorization/API requirements are confirmed and the first integration is stable. This is a proposed scope reduction and requires the platform decision/requirements traceability to be updated before treating fewer platforms as approved scope.
- Per-platform attempt history, idempotency/duplicate prevention where the external API permits it, bounded transient retries, and explicit unknown/ambiguous outcomes.
- Useful user notifications for action-required and terminal publishing outcomes, without building a general notification platform.
- Basic content/publishing history and a small set of analytics metrics actually exposed by the selected platform API.
- Structured application logs with correlation identifiers and secret/PII redaction.
- PostgreSQL, migrations, Docker-based local setup, environment validation, automated tests, CI checks, setup documentation, and a short architecture/trade-off document.

### Engineering quality gates
- Owner-scoped querysets/services and cross-user access-denial tests.
- Credential encryption or a secure provider-native OAuth/token-storage approach, with secrets never returned by read APIs or written to logs.
- Safe outbound requests and XML parsing for RSS/Atom; provider terms and content-retention rules must be checked before enabling each adapter.
- Unit tests for domain rules, adapter contract tests with fixtures, PostgreSQL integration/migration tests, and end-to-end tests for the critical workflow.
- Tests for provider outages, invalid credentials, rate limits, partial success, duplicate requests, stale approval, and cross-user access.
- No test database deletion/recreation as a shortcut. Preserve existing Git state; no automatic staging, commit, or push.

## 4. Research quality requirements (do not cut)

- Query construction should reflect topic, audience, platform, date window, and user intent; query broadening must be bounded and visible.
- RSS/Atom and GNews adapters should normalize results into a common, typed representation while preserving provider/source identity and attribution.
- Deduplicate by canonical URL and use conservative story similarity for near-duplicates; retain provenance when merging duplicates rather than silently discarding sources.
- Rank results using explainable factors such as topical relevance, recency, source quality signals, and corroboration. Do not imply that a publisher is trustworthy solely because it is present in a feed or API.
- Where claims are consequential or sources conflict, show disagreement and request more evidence rather than synthesizing false certainty. Corroboration means genuinely independent sources, not syndications of the same wire story.
- Separate source metadata, short permitted excerpts, extracted claims, and generated content. Preserve links and attribution; do not store or republish full article text by default.
- Feed evidence to generation in a bounded, relevant context with source IDs/URLs so review can check claim-to-source alignment. The model must not invent citations or attribute claims to sources that do not support them.
- Make retrieval time windows, filters, result limits, exclusions, and failed providers visible. Preserve successful results when another source fails and mark partial results honestly.
- Measure usefulness with practical checks: relevance of top results, duplicate rate, freshness, source coverage, unsupported-claim rate in generated drafts, and source-attribution accuracy. Use fixtures and evaluation cases; do not claim objective “best content” without an evaluation method.
- Respect provider terms, rate limits, feed-specific access restrictions, and retention requirements. Public availability does not grant republication rights.

## 5. Simplify or defer

| Capability | Scope decision | Reason / revisit trigger |
|---|---|---|
| Additional research providers (NewsAPI, Tavily, Reddit, GitHub, YouTube, generic web search) | Defer; preserve a small adapter boundary | Add only when a demonstrated workflow needs them and terms/cost are verified. |
| Multiple AI vendors at launch | Support one working default provider first; keep the integration boundary replaceable | Add a second provider only to demonstrate a real fallback or user choice, not just provider count. |
| Image generation and media storage | Defer until text workflow, approval, and publishing are reliable; then add one image path if supported-platform requirements justify it | Image pipelines add cost, storage, moderation, and platform constraints. |
| Full template-management subsystem | Defer or keep only a few built-in reusable templates | A custom template CRUD product is not central to proving the core workflow. |
| Advanced research refinement, cache controls, and complex query lineage | Simplify to query history, saved results, deduplication, and basic re-query | Keep refinement only if it materially improves research-to-content use. |
| Advanced analytics dashboards | Defer; show basic counts/statuses and metrics supported by the chosen platform | Avoid inventing metrics or building a reporting subsystem without data. |
| Enterprise administration, team/organization roles, billing, multi-tenancy beyond safe user isolation | Defer | Not required for an individual portfolio application. |
| Microservices and a large plugin framework | Cut | A well-structured Django modular monolith is simpler to test and explain. |
| Redis/Celery or another task broker before proven need | Defer until latency/reliability requirements justify it | Do not add infrastructure by assumption; use bounded synchronous operations only where safe, otherwise introduce one approved background-job system. |
| Kubernetes, multi-region, autoscaling, elaborate AWS topology | Defer | Demonstrate Docker, CI, configuration, migrations, backup/restore guidance, and a deployment path first. |
| Public production deployment, paid subscriptions, paid trials | Defer | The repository must be deployable, but public operation is not necessary for resume credibility. No purchase/trial/live commercial activation without explicit approval. |
| OAuth2 tasks unrelated to the selected platform/provider's actual auth flow | Defer | Implement only the authorization flow required by selected integrations. |

## 6. Non-negotiable behavior

Do not cut these to reduce scope:
- Authentication and user-data isolation.
- Server-side authorization on every user-owned resource.
- Explicit human approval before publishing; edits invalidate approval for the changed version.
- Bounded AI revision and bounded retries.
- Accurate publishing status; never report success without provider confirmation.
- Per-platform independent results and explicit handling of ambiguous external state.
- Credential/secret protection and log redaction.
- Input validation, provider timeouts, rate limits, and safe external requests.
- Database migrations, regression tests, and a reproducible local setup.

## 7. Scope decisions that require formal change control

This document is a scope proposal and does not silently override `REQUIREMENTS.MD`.

Before implementation scope is reduced, update the authoritative requirement and traceability artifacts for:
1. The initial social-platform count and exact platform(s), currently unresolved under UD-001.
2. Whether recurring campaigns are part of the first demonstrable release or follow after one-time scheduling/publishing is stable.
3. Which AI review stages and analytics requirements are mandatory in the reduced release versus later releases.
4. Whether media/image generation is needed for the first complete workflow.
5. Which OAuth2 tasks are genuinely required by the selected integration(s).

For every approved scope change, record the affected requirement/acceptance criterion, old behavior, new behavior, rationale, test impact, design impact, and deferred-release target. Do not mark a deferred requirement as complete.

## 8. Delivery order

1. Close only the design blockers that affect correctness/security: content snapshot versus approval state, shared lifecycle transition behavior/API, selected platform/authentication, credential protection, and provider request contracts.
2. Verify the existing foundation and test setup without destructive database operations.
3. Finish versioning and approval invariants with tests.
4. Build one research vertical slice with fake-provider tests, then enable RSS/Atom safely; keep GNews live calls gated by terms and explicit activation approval.
5. Complete generation → review → bounded correction → validation → approval.
6. Complete one direct publishing adapter end to end, including failure, retry, idempotency, and audit behavior.
7. Add scheduling, then recurring campaigns if still in the approved first-release scope.
8. Add only the history, notification, and basic analytics needed to make the workflow usable and demonstrable.
9. Run regression, security, migration, and end-to-end tests; document measured results and known limitations.
10. Review whether deferred features add enough resume value to justify their cost before expanding scope.

## 9. Frontend and dashboard direction

The frontend must look deliberate and polished; visual quality is part of the portfolio deliverable. Keep the interaction surface small rather than removing useful product behavior. Use the existing Django Templates + HTMX direction, not a separate React/Next.js rewrite. Build a consistent responsive design system with clear typography, restrained color, spacing, accessible contrast, empty/loading/error/success states, useful research filters, readable source cards, visible provenance, and a clear content-review/approval/publishing flow. Prefer a focused research workspace and content pipeline over a crowded analytics dashboard. Avoid decorative charts, fake metrics, unnecessary settings pages, and features that have no working backend.

Authentication is not a throwaway dashboard feature: retain secure login/logout and server-side authorization. For a local demo, make the setup simple and document demo-account creation; do not remove authentication or user isolation to save UI work.

## 10. Definition of done

The project is portfolio-ready when a reviewer can clone it, configure development credentials, start it reproducibly, run tests, and demonstrate the complete approved workflow. The README must distinguish verified capabilities from mocked integrations, untested live integrations, deferred features, and production-only operational tasks. No claim of production readiness is made without evidence.
