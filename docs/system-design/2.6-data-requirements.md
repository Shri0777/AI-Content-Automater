## 2.6.1 Purpose

### What Are Data Requirements?

Data requirements define **WHAT information the system must create, receive, store, update, retrieve, protect, audit, and derive** to satisfy the authoritative business requirements.

This document answers:
- **What data must exist?** (conceptual entities)
- **What information must be preserved?** (attributes at conceptual level)
- **What relationships exist between data?** (conceptual relationships)
- **What data ownership, lifecycle, validation, and integrity rules apply?** (business-level constraints)

This document does NOT answer:
- **How will data be physically stored?** (SQL tables, columns, indexes)
- **Which database technology will be used?** (PostgreSQL specifics, Redis, etc.)
- **What ORM models will represent the data?** (Django models, Prisma schema)
- **What is the exact JSON structure?** (API payloads, cache structures)
- **What AWS services will store the data?** (S3, RDS, DynamoDB decisions)

### Objectives

This data requirements analysis:

1. **Identifies** all information required to support functional requirements, business rules, use cases, and domain concepts
2. **Defines** conceptual data entities, attributes, and relationships
3. **Specifies** data ownership, lifecycle, sensitivity, validation, and integrity requirements
4. **Establishes** clear distinction between source-of-truth data, derived data, and external data
5. **Traces** data requirements to authoritative requirements
6. **Documents** unresolved data decisions explicitly
7. **Provides** the conceptual data foundation for system design

## 2.6.2 Data Analysis Principles

### Core Principles

**Requirements Are Authoritative:**
All data requirements derive from REQUIREMENTS.MD V2.0. Data not supported by requirements shall not be invented.

**Data Requirements Describe Business Information:**
This document describes WHAT information exists and WHY it's needed from a business perspective, not HOW it will be stored technically.

**Implementation Decisions Are Deferred:**
Database engine selection, table design, column types, indexes, caching strategies, and storage services are system design decisions, not data requirements.

**Only Necessary Data Should Be Retained:**
System shall collect and store only information required by product functionality (Section 54). Avoid unnecessary data collection.

**Data Ownership Must Be Explicit:**
Every user-owned resource has clear ownership (Section 9, BR-001). System-owned and externally-owned data distinguished.

**Sensitive Data Requires Appropriate Protection:**
Authentication credentials, authorization tokens, secrets, and user content must be identified and protected (BR-016, NFR-001).

**Historical/Audit Information Must Remain Distinguishable:**
Current operational state must be clearly distinguishable from historical records, audit trails, and analytics (Sections 43, 44).

**Derived Information Must Not Be Confused with Source-of-Truth:**
Publishing eligibility, overall publishing status, and analytics are DERIVED from authoritative data, not source-of-truth themselves.

**Unresolved Requirements Must Not Be Invented:**
When requirements do not specify data details (e.g., exact revision limit numeric value), document as unresolved rather than inventing values.

### Data vs. Domain Concepts

**Domain Concept (from 2.5):**
Conceptual business entity in the problem domain.
Example: DC-003 Content, DC-010 Approval

**Data Requirement (this document):**
Information that must be represented to support domain concepts.
Example: Content identity, ownership, lifecycle state, title, topic, target platforms; Approval timestamp, approved version reference, approver identity

**Not all domain concepts require dedicated data entities.**
Example: DC-013 Publishing Eligibility is a DERIVED state aggregating other data, not a separately stored entity.

### Data Categories

This analysis distinguishes:

1. **Identity Data:** User accounts, authentication, authorization context
2. **Ownership Data:** Resource-owner relationships
3. **Operational Data:** Current system state (content, schedules, campaigns, publishing)
4. **Versioned Data:** Content versions, version-specific approvals
5. **Historical Data:** Past events, version history, change records
6. **Derived Data:** Computed from other data (eligibility, aggregated status, analytics)
7. **External Data:** Received from external systems (AI responses, platform results, research)
8. **Audit Data:** Security-sensitive event records
9. **Configuration Data:** System settings, integration configuration (where explicitly required)
10. **Sensitive Data:** Credentials, tokens, secrets (requires protection)

## 2.6.4 Data Entity Catalog

### DE-001: User Account Data

**Data ID:** DE-001
**Data Name:** User Account
**Definition:** Identity and authentication information for system users

**Business Purpose:**
- Authenticate users before protected operations
- Establish ownership context for content, campaigns, and integrations
- Enable authorization decisions
- Support user resource isolation (BR-001)

**Source:** User registration, administrator provisioning

**Owner:** Self-owned user identity

**Consumers:**
- Authentication subsystem
- Authorization subsystem
- All user-owned resource operations

**Required / Optional:** Required for all protected functionality

**Lifecycle:**
- Created at user registration
- Active throughout user engagement
- Credentials updated as needed
- Account may be disabled/deleted (requirements do not specify retention)

**Sensitivity:** **Highly Sensitive**
- Authentication credentials (passwords, hashed)
- Email addresses
- Personal identification information

**Validation Requirements:**
- Username/email uniqueness
- Password strength (framework secure password storage - Section 7)
- Valid email format

**Integrity Requirements:**
- User identity stable across sessions
- Ownership relationships preserved
- Authentication failures not disclosing sensitive information (Section 7)

**Retention Requirement:** Not explicitly specified (requires design decision)

**Audit Requirement:** Authentication events audited (Section 44)

**Related Domain Concept:** DC-001 (User)

**Related Business Rules:** BR-001 (User Resource Isolation), BR-016 (Secrets Not Exposed)

**Related Use Cases:** UC-001 (Authenticate User), UC-002 (Authorize Resource Access)

**Related FRs:** FR-001 (Authentication), FR-002 (Authorization)

**Related NFRs:** NFR-001 (Security), NFR-010 (Auditability)

**Dependencies:** Framework secure password storage

**Open Questions:**
- User account deletion/retention policy
- Password reset mechanisms
- Multi-factor authentication support (not mentioned in requirements)

## 2.6.28 Data Integrity Requirements

### Version-Aware Approval Integrity

**Requirement:** Approval for version N does NOT authorize publishing version N+1.

**Enforcement Data:**
- Approval.Approved_Version_ID references specific Content Version
- Publishing checks current Content.Current_Version_ID matches Approval.Approved_Version_ID
- Version mismatch blocks publication

**Business Rule:** BR-007 (Material Edits Invalidate Approval)

**Verification:** Publishing eligibility checks version match

---

### Multi-Platform Result Independence

**Requirement:** Platform A result cannot be overwritten by Platform B result.

**Enforcement Data:**
- Platform Publishing Result.Platform_ID distinguishes results
- Each result has unique Result_ID
- Results immutable once created
- Platform-specific result storage

**Business Rules:** BR-010 (Independent Per-Platform Results), BR-011 (Platform Result Independence)

**Verification:** Independent result creation, no overwrite logic

---

### Bounded Revision Enforcement

**Requirement:** Automated correction/review cycles cannot execute indefinitely.

**Enforcement Data:**
- Revision Counter.Current_Count tracks attempts
- Revision Counter.Maximum_Limit defines bound
- Revision Counter.Exhaustion_State flags limit reached

**Business Rule:** BR-003 (Finite AI Revision Loops)

**Verification:** Counter checked before allowing correction

---

### Scheduled Content Revalidation

**Requirement:** Content eligible when scheduled must be revalidated at execution time.

**Enforcement Data:**
- Schedule.Eligibility_State_At_Scheduling captured
- Execution-time eligibility rechecked against current state
- Eligibility check includes: validation, approval, reviews, platform authorization, media

**Business Rule:** BR-008 (Scheduled Content Revalidation at Execution Time)

**Verification:** Scheduler rechecks all eligibility conditions before publishing

---

### Ownership Consistency

**Requirement:** Ownership relationships remain consistent; users cannot access other users' resources.

**Enforcement Data:**
- Content.Owner_User_ID identifies owner
- All operations check ownership
- Authorization checks user matches owner or has permission

**Business Rule:** BR-001 (User Resource Isolation)

**Verification:** Every resource access checks ownership

---

### Historical Record Attributability

**Requirement:** Historical records remain attributable to actors and operations.

**Enforcement Data:**
- Audit Record.Actor identifies who
- Audit Record.Action identifies what
- Audit Record.Timestamp identifies when
- Version history chain preserved

**Business Rule:** Traceability (Section 10, Section 43)

**Verification:** Audit trail complete, version history intact

---

### Duplicate Publication Prevention

**Requirement:** Retries must not cause duplicate publications.

**Enforcement Data:**
- Publishing Attempt.Stable_Job_Identity for duplicate detection
- Platform idempotency tokens (where available)
- Application-level locking/uniqueness

**Business Rule:** BR-012 (Bounded and Duplicate-Safe Retries)

**Verification:** Stable job identity prevents duplicate processing
