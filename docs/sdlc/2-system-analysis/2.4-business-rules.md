## 2.4.1 Purpose

This document provides the **Business Rules Analysis** for the AI Content Automater system.

Business rules define the **constraints, policies, invariants, and operational rules** that govern system behavior. They represent WHAT must be enforced, regardless of HOW the system is implemented.

## 2.4.2 Business Rule Principles

### What is a Business Rule?

A business rule is an enforceable business constraint, policy, invariant, eligibility condition, authorization rule, lifecycle rule, or operational rule that governs system behavior.

Business rules are:

- **Business-driven** — Derived from product requirements, not technical preferences
- **Implementation-independent** — Apply regardless of technology choices
- **Testable** — Can be verified through automated or manual testing
- **Traceable** — Map to specific requirements and use cases
- **Enforceable** — System must prevent rule violations

### What is NOT a Business Rule?

The following are NOT business rules:

- Database schema design
- Table structures or indexes
- Class hierarchies
- API endpoint definitions
- Framework behaviors
- Django model implementations
- Celery task configurations
- Redis caching strategies
- AWS service selections
- UI component structures

These are implementation decisions that support business rules but are not rules themselves.

### Core Principles

**Requirements are Authoritative:** All business rules derive from REQUIREMENTS.MD V2.0. Rules not supported by requirements are either unresolved decisions or scope creep.

**Rules Apply Universally:** Business rules apply regardless of implementation technology. Changing from Django to another framework does not change the business rules.

**AI Cannot Bypass Controls:** Automation, including AI-driven workflows, must respect all mandatory quality, validation, authorization, and publishing controls (REQUIREMENTS.MD Section 76).

**Rules Must Be Testable:** Every business rule must be verifiable. V1 acceptance criteria require proof that mandatory gates cannot be bypassed (REQUIREMENTS.MD Section 73, criterion #26).

**Unresolved Decisions Must Not Be Invented:** Items not specified in requirements (e.g., exact revision limit numeric value) must be marked as unresolved, not silently decided during analysis or implementation.

### BR-001: User Resource Isolation

**Rule ID:** BR-001  
**Rule Name:** User Resource Isolation  
**Source:** REQUIREMENTS.MD Section 69

**Rule Statement:**  
Users cannot access another user's protected resources without explicit authorization.

**Rationale:**  
Protects user privacy, data security, and multi-tenant data isolation. Prevents unauthorized access to content, campaigns, schedules, publishing information, credentials, and analytics.

**Trigger / Condition:**  
Any attempt by an authenticated user to access a resource owned by a different user.

**Enforcement Condition:**  
System SHALL:
- Verify ownership on every resource access request
- Deny access when user does not own resource and lacks explicit permission
- Prevent insecure direct object reference attacks (Section 9)
- Enforce authorization server-side (Section 8)

**Result / Consequence:**
- **Authorized:** User gains access to resource
- **Unauthorized:** Access denied, no protected data exposed, request fails safely (Section 8)

**Scope:**  
Applies to all user-owned resources:
- Content items
- Research records
- Content versions
- AI review results
- Approvals
- Schedules
- Campaigns
- Publishing jobs
- Platform connections (social accounts)
- Media
- Notifications
- Analytics data
- Audit records (except administrative access)

**Related Actors:**
- User (subject to isolation rules)
- Administrator (can access with auditable administrative authorization)

**Related Use Cases:**
- UC-002: Authorize Resource Access
- All use cases involving user-owned resources

**Related Functional Requirements:**
- FR-002: Authorization

**Related Non-Functional Requirements:**
- NFR-001: Security — Protected resources must be secured

**Related Data Concepts:**
- User ownership
- Resource ownership relationships
- Access control metadata

**Related Lifecycle States:**
- Applies to all lifecycle states

**Dependencies:**
- Authentication (user must be authenticated first)
- Ownership tracking on all user-owned entities

**Exceptions / Alternative Conditions:**
- Administrative users may access user resources with appropriate administrative authorization (Section 8)
- Administrative access must be deliberate and auditable (Section 9)
- Explicit resource sharing (if implemented) requires defined authorization rules

**Unresolved Decisions:**
- Exact permission model beyond owner/administrator
- Resource sharing mechanisms (if any)
- Granularity of access control (resource-level, operation-level, field-level)

### BR-002: Mandatory AI Review Sequence

**Rule ID:** BR-002  
**Rule Name:** Mandatory AI Review Sequence  
**Source:** REQUIREMENTS.MD Section 69

**Rule Statement:**  
Mandatory AI reviews must occur before final validation.

**Rationale:**  
Ensures content quality through automated quality control gates. Prevents publication of content that has not been subjected to required quality review processes.

**Trigger / Condition:**  
Content progresses from generation toward final validation and approval.

**Enforcement Condition:**  
System SHALL:
- Execute AI Review #1 after generation (Section 17)
- Execute correction when Review #1 identifies issues (Section 19)
- Execute AI Review #2 after correction (Section 20)
- Block advancement to final validation until both review stages complete successfully
- NOT bypass reviews merely because generated content appears acceptable (Section 17)

**Required Sequence:**  
Generation → AI Review #1 → Correction (if needed) → AI Review #2 → Final Validation

**Result / Consequence:**
- **Reviews Pass:** Content proceeds to final validation
- **Review Fails:** Content subject to bounded revision rules (BR-003)
- **Reviews Bypassed:** System prevents advancement; publication blocked

**Scope:**  
Applies to:
- All AI-generated content
- Manual content workflows using AI generation
- Automated campaign content workflows

**Related Actors:**
- AI Service (performs reviews)
- User (initiates generation)
- Scheduler (triggers automated campaigns)

**Related Use Cases:**
- UC-007: Generate Content with AI
- UC-008: Perform AI Review #1
- UC-009: Correct Content Based on Review
- UC-010: Perform AI Review #2
- UC-011: Enforce Revision Limit

**Related Functional Requirements:**
- FR-006: AI Generation
- FR-007: AI Review #1
- FR-008: AI Correction
- FR-009: AI Review #2

**Related Non-Functional Requirements:**
- NFR-002: Reliability — Critical workflows must preserve consistent state

**Related Data Concepts:**
- Content version
- Review results
- Review stage tracking
- Workflow state

**Related Lifecycle States:**
- Generated (after generation, before Review #1)
- Under Review (during review stages)
- Correction (between reviews)
- Reviewed (after successful Review #2)

**Dependencies:**
- AI Service availability
- BR-003 (Bounded revision loops)
- FR-010 (Revision limit enforcement)

**Exceptions / Alternative Conditions:**
- None — Reviews are mandatory and cannot be bypassed
- Manual content creation that does not use AI generation may follow different rules (not specified in requirements)

**Unresolved Decisions:**
- Exact AI review rubric (Section 74)
- Review scoring methodology
- Thresholds for passing/failing reviews
- Behavior when AI service permanently unavailable

### BR-003: Finite AI Revision Loops

**Rule ID:** BR-003  
**Rule Name:** Finite AI Revision Loops  
**Source:** REQUIREMENTS.MD Section 69

**Rule Statement:**  
AI correction/review loops must be finite.

**Rationale:**  
Prevents unbounded autonomous operation that could waste resources, create uncontrolled costs, or never complete. Ensures human intervention when AI cannot produce acceptable content within reasonable bounds.

**Trigger / Condition:**  
AI Review #2 identifies issues requiring correction.

**Enforcement Condition:**  
System SHALL:
- Maintain a revision counter for each content item (Section 21)
- Have a configured maximum revision count (Section 21)
- Increment counter on each correction attempt
- Compare counter against maximum before allowing another revision
- When limit exhausted:
  - STOP automated revision (Section 21)
  - BLOCK automatic publishing (Section 21)
  - Enter intervention or failed state (Section 21)
  - Record reason (Section 21)

**Result / Consequence:**
- **Under Limit:** Correction proceeds, counter increments, Review #2 re-executes
- **At Limit:** Automated revision stops, publishing blocked, human intervention required

**Scope:**  
Applies to:
- Automated correction/review cycles
- All content using AI generation
- Both manual and campaign-driven workflows

**Related Actors:**
- AI Service (performs corrections)
- User (receives notification when limit exhausted)

**Related Use Cases:**
- UC-009: Correct Content Based on Review
- UC-010: Perform AI Review #2
- UC-011: Enforce Revision Limit

**Related Functional Requirements:**
- FR-008: AI Correction
- FR-009: AI Review #2
- FR-010: Revision Limit

**Related Non-Functional Requirements:**
- NFR-002: Reliability — Workflows must fail safely

**Related Data Concepts:**
- Revision counter
- Maximum revision configuration
- Workflow state
- Intervention state

**Related Lifecycle States:**
- Correction (during revision loop)
- Intervention Required (when limit exhausted)
- Failed (when limit exhausted without resolution)

**Dependencies:**
- BR-002 (Mandatory review sequence)
- FR-007, FR-008, FR-009 (Review and correction functions)

**Exceptions / Alternative Conditions:**
- Manual user intervention after limit exhaustion may reset counter (behavior not specified)
- User may manually edit and resubmit (treated as new version)

**Unresolved Decisions:**
- Exact numeric revision limit value (Section 74)
- Behavior after limit exhausted (discard, hold for manual review, notify and wait?)
- Whether manual fixes can reset counter

### BR-004: Failed Quality Gates Block Publication

**Rule Name:** Failed Quality Gates Block Publication

Failed mandatory quality gates block publication.

System SHALL:
- NOT advance content beyond a failed gate

**Mandatory Quality Gates:**
1. AI Review #1 (Section 17, 18)
2. AI Review #2 (Section 17, 20)

**Result / Consequence:**

**Scope:**

- Automated campaign workflows
- Scheduled content (re-checked at execution time per BR-008)

**Related Actors:**
- AI Service (performs reviews)

**Related Use Cases:**

**Related Functional Requirements:**

**Related Non-Functional Requirements:**

**Related Data Concepts:**
- Content lifecycle state
- Review results

**Related Lifecycle States:**

**Dependencies:**

### BR-007: Material Edits Invalidate Approval

**Rule ID:** BR-007  
**Rule Name:** Material Edits Invalidate Approval  
**Source:** REQUIREMENTS.MD Section 69

**Rule Statement:**  
Material edits invalidate affected approval.

**Rationale:**  
Ensures approval applies to actual content being published, not an obsolete version. Prevents publishing unapproved changes by exploiting old approval records.

**Trigger / Condition:**  
User makes material edit to content after approval has been granted.

**Enforcement Condition:**  
System SHALL:
- Tie approval to specific content version (Section 25, Section 12)
- Detect material changes after approval
- Invalidate approval when material edit occurs (Section 12, Section 23)
- Return content to appropriate quality gate (Section 23)
- NEVER publish obsolete approved version when newer unapproved version exists (Section 12)

**Material Edit Definition:**  
A material edit is a change that makes the previous approval no longer applicable (Section 12). Examples might include:
- Changing content text
- Changing target platforms
- Changing media
- Other substantive changes

**Result / Consequence:**
- **Material Edit Detected:** Approval invalidated, content returns to appropriate workflow stage (validation, review, or correction)
- **Non-Material Edit:** Approval may remain valid (behavior not specified in requirements)

**Scope:**  
Applies to:
- All approved content that is edited before publication
- Manual edits by users
- Any modification that changes the approved version

**Related Actors:**
- User (makes edits)
- System (detects and enforces invalidation)

**Related Use Cases:**
- UC-005: Edit Content Item
- UC-013: Approve Content for Publication (creates version-specific approval)

**Related Functional Requirements:**
- FR-004: Content Editing
- FR-012: Approval

**Related Non-Functional Requirements:**
- NFR-008: Data Integrity — State must be accurate

**Related Data Concepts:**
- Content version
- Approval record (tied to specific version)
- Version history
- Edit timestamp

**Related Lifecycle States:**
- Approved (invalidated when material edit occurs)
- Returns to earlier state (Validated, Reviewed, or Correction depending on edit)

**Dependencies:**
- BR-006 (Approval required)
- Content versioning system

**Exceptions / Alternative Conditions:**
- Minor non-material edits may not invalidate approval (requirements state "when the previous approval no longer applies")
- Exact definition of "material" left to design phase

**Unresolved Decisions:**
- Exact definition of "material edit" vs. non-material edit
- Which edits invalidate approval (all? only content text? metadata changes?)
- Whether system automatically detects materiality or requires manual judgment

### BR-008: Scheduled Content Revalidation at Execution Time

**Rule ID:** BR-008  
**Rule Name:** Scheduled Content Revalidation at Execution Time  
**Source:** REQUIREMENTS.MD Section 69

**Rule Statement:**  
Scheduled content must be revalidated at execution time.

**Rationale:**  
Content that was eligible when scheduled may become ineligible before execution. Platform credentials may expire, content may be edited, approval may be revoked, or other conditions may change. Execution-time validation prevents publishing ineligible content.

**Trigger / Condition:**  
Scheduler reaches scheduled execution time for content publication.

**Enforcement Condition:**  
System SHALL:
- Re-check publication eligibility at execution time (Section 29)
- Verify all mandatory conditions still true (Section 26):
  - Content is valid
  - Required AI reviews completed
  - Required corrections completed
  - Final validation passed
  - Required approval exists
  - Target platform is authorized
  - Required content/media is available
  - Scheduled execution is valid
- Refuse publication if any condition no longer true (Section 27)
- Keep schedule in pending/error state until eligibility restored

**Result / Consequence:**
- **Still Eligible:** Publishing proceeds
- **No Longer Eligible:** Publishing blocked, schedule remains pending, user may be notified

**Scope:**  
Applies to:
- All scheduled content
- Recurring campaign content
- Both manual and automated workflows

**Related Actors:**
- Scheduler (performs revalidation)
- User (may need to fix eligibility issues)

**Related Use Cases:**
- UC-014: Schedule Content for Publication (creates schedule)
- UC-019: Publish Content to Platform (executes with revalidation)

**Related Functional Requirements:**
- FR-013: Scheduling
- FR-015: Direct Publishing

**Related Non-Functional Requirements:**
- NFR-002: Reliability
- NFR-008: Data Integrity

**Related Data Concepts:**
- Schedule record
- Publishing eligibility
- Platform authorization status
- Content validation status

**Related Lifecycle States:**
- Scheduled (waiting for execution)
- Publishing (during execution)

**Dependencies:**
- BR-004 (Gates must pass)
- BR-005 (Validation required)
- BR-006 (Approval required)
- BR-007 (Edits invalidate approval)

**Rule Statement:**  
Publishing outcomes are tracked independently per platform.

**Rationale:**  
Content targeting multiple platforms must track each platform's result separately. Prevents loss of information when one platform succeeds and another fails. Enables accurate reporting and retry logic.

**Trigger / Condition:**  
Content targets multiple platforms for publication.

System SHALL:
- Track independent publishing attempt per platform (Section 34)
- Record independent result per platform
- Distinguish platform-specific outcomes (Section 34):
  - Platform A: Published
  - Platform B: Failed

- Aggregate overall status from individual results
- NOT overwrite one platform's result with another's (BR-011)

**Result / Consequence:**
- Each platform has own result record
- Overall content status distinguishes:
  - All-successful
  - Partially-successful
  - All-failed
  - Pending
  - Cancelled (Section 34)

**Scope:**  
Applies to:
- All multi-platform content
- All publishing operations
- Manual and automated workflows

**Related Actors:**
- Publishing Integration (one per platform)
- Scheduler (initiates multi-platform publishing)

**Related Use Cases:**
- UC-019: Publish Content to Platform

**Related Functional Requirements:**
- FR-015: Direct Publishing
- FR-016: Platform Tracking

**Related Non-Functional Requirements:**

**Related Data Concepts:**
- Per-platform publishing result
- Overall content publishing status
- Platform-specific timestamps
- Platform-specific failure reasons

**Related Lifecycle States:**
- Published (all platforms succeeded)

### BR-011: Platform Result Independence

**Rule ID:** BR-011  
**Rule Name:** Platform Result Independence  
**Source:** REQUIREMENTS.MD Section 69

**Rule Statement:**  
A failed platform publication must not overwrite another platform's successful result.

**Rationale:**  
Preserves accurate publishing history. Prevents incorrect reporting where partial success is lost due to later failure on another platform. Critical for retry logic and analytics.

**Trigger / Condition:**  
Multi-platform content publishes, and platforms have different outcomes.

**Enforcement Condition:**  
System SHALL:
- Maintain independent result storage per platform
- NEVER overwrite Platform A's result when recording Platform B's result
- Preserve successful publication records even when other platforms fail (Section 34)
- Maintain result immutability per platform
- Update only overall aggregated status

**Result / Consequence:**
- Platform-specific results remain accurate
- Successful publications remain recorded even if other platforms fail
- Retry logic can target only failed platforms

**Scope:**  
Applies to:
- All multi-platform publishing
- All publishing operations
- Success and failure states

**Related Actors:**
- Publishing Integration (each platform integration operates independently)

**Related Use Cases:**
- UC-019: Publish Content to Platform
- UC-020: Track Multi-Platform Publishing Results
- UC-021: Retry Failed Publishing (retries only failed platforms)

**Related Functional Requirements:**
- FR-015: Direct Publishing
- FR-016: Platform Tracking
- FR-017: Publishing Retry

**Related Non-Functional Requirements:**
- NFR-008: Data Integrity

**Related Data Concepts:**
- Per-platform result immutability
- Result timestamps
- Overall status aggregation logic

**Related Lifecycle States:**
- Partially Published (critical state requiring this rule)

**Dependencies:**
- BR-010 (Independent per-platform tracking)

**Exceptions / Alternative Conditions:**
- None — Results must remain independent

**Unresolved Decisions:**
- None — Requirements are clear

### BR-012: Bounded and Duplicate-Safe Publishing Retries

**Rule ID:** BR-012  
**Rule Name:** Bounded and Duplicate-Safe Publishing Retries  
**Source:** REQUIREMENTS.MD Section 69

**Rule Statement:**  
Publishing retries must be bounded and duplicate-safe.

**Rationale:**  
Prevents infinite retry loops that waste resources and may cause duplicate publications. Ensures retries respect idempotency and do not blindly resubmit operations that may have partially succeeded.

**Trigger / Condition:**  
Publishing attempt fails with retryable error.

**Enforcement Condition:**  
System SHALL:
- Limit number of retry attempts (bounded) (Section 37)
- NOT retry indefinitely (Section 37)
- Preserve duplicate-publication protection during retries (Section 37)
- NOT blindly resubmit same operation repeatedly (Section 35)
- Use stable job identity for duplicate detection (Section 35)
- Use platform idempotency features where available (Section 35)
- Use application-level state locking and uniqueness constraints (Section 35)
- Distinguish retry-worthy failures from permanent failures (Section 37)
- Handle authentication failures differently from transient API failures (Section 37)
- Re-check content eligibility before retry (Section 37)

**Result / Consequence:**
- **Retry Succeeds:** Publishing completes, result recorded

## 2.4.4 Core Content Lifecycle Rules

This section analyzes business rules governing content as it progresses through the complete lifecycle:

**Draft → Researching → Generated → AI Review #1 → Correction → AI Review #2 → Final Validation → Approved → Scheduled → Publishing → Published / Partially Published / Failed**

### Lifecycle State Transitions

**State:** Draft  
**Entry Condition:** User creates content (UC-004)  
**Permitted Transitions:**
- Draft → Researching (when user initiates research)
- Draft → Generated (when user initiates generation without research)

**Business Rules:**
- Content belongs to creating user (BR-001)
- User can edit content freely in Draft state

---

**State:** Researching  
**Entry Condition:** User or campaign initiates research  
**Permitted Transitions:**
- Researching → Generated (when research completes and generation initiates)
- Researching → Failed (when research fails unrecoverably)

**Business Rules:**
- Research failure blocks dependent generation when research is mandatory (Section 14)
- Failed research must be recorded accurately (BR-013)
- System shall never fabricate research results (Section 14)

---

**State:** Generated  
**Entry Condition:** AI generation completes successfully  
**Permitted Transitions:**
- Generated → Under Review (AI Review #1 initiated)
- Generated → Failed (when generation failure detected)

**Business Rules:**
- AI Review #1 is mandatory before advancing (BR-002)
- Generation cannot be bypassed
- Generated content distinguishable from manual edits (Section 15)

---

**State:** Under Review (AI Review #1)  
**Entry Condition:** Generated content enters first review  
**Permitted Transitions:**
- Under Review → Correction (when Review #1 identifies issues)
- Under Review → Under Review (AI Review #2) (when Review #1 passes without issues)

**Business Rules:**
- Review #1 cannot be bypassed (BR-002, Section 17)
- Review operates on known content version (Section 17)
- Review result must be traceable (Section 17)

---

**State:** Correction  
**Entry Condition:** AI Review #1 identifies correctable issues  
**Permitted Transitions:**
- Correction → Under Review (AI Review #2) (when correction completes)
- Correction → Intervention Required (when revision limit exhausted per BR-003)

**Business Rules:**
- Bounded revision loops enforced (BR-003)
- Revision counter incremented (Section 21)
- Correction operates on reviewed version and findings (Section 19)
- Correction creates new version without erasing history (Section 19)

---

**State:** Under Review (AI Review #2)  
**Entry Condition:** Content has completed Review #1 and any required correction  
**Permitted Transitions:**
- Under Review → Validated (when Review #2 passes)
- Under Review → Correction (when Review #2 fails and revision limit not exhausted)
- Under Review → Intervention Required (when Review #2 fails and revision limit exhausted)

**Business Rules:**
- Review #2 is mandatory before final validation (BR-002)
- Review #2 operates on latest corrected content (Section 20)
- Revision limit enforced (BR-003)
- Failed review invokes bounded revision rules (Section 20)

---

**State:** Validated  
**Entry Condition:** AI Review #2 passes and final validation executes and passes  
**Permitted Transitions:**
- Validated → Approved (when manual approval granted)
- Validated → Scheduled (when automated validation used and approval not required)
- Validated → Validation Failed (when final validation fails)

**Business Rules:**
- Final validation is mandatory before publication (BR-005)
- All mandatory publication conditions must be checked (Section 24)
- Failed validation blocks publication (BR-004, BR-005)

---

**State:** Approved  
**Entry Condition:** Authorized user grants approval  
**Permitted Transitions:**
- Approved → Scheduled (when user schedules publication)
- Approved → Validated (when material edit invalidates approval per BR-007)
- Approved → Under Review (when material edit requires re-review)

**Business Rules:**
- Approval tied to specific content version (BR-006, BR-007, Section 25)
- Material edits invalidate approval (BR-007)
- Approval actions recorded (Section 25)
- Approval required where configured (BR-006)

---

**State:** Scheduled  
**Entry Condition:** Approved/validated content scheduled for future publication  
**Permitted Transitions:**
- Scheduled → Publishing (when scheduled time arrives and eligibility confirmed)
- Scheduled → Ineligible (when execution-time validation fails)

**Business Rules:**
- Only eligible content may be scheduled (Section 27)
- Content revalidated at execution time (BR-008)
- Scheduler refuses publication if eligibility lost (Section 27)
- Timezone must be explicit (Section 28)

---

**State:** Publishing  
**Entry Condition:** Scheduled time arrives, eligibility confirmed, publishing initiated  
**Permitted Transitions:**
- Publishing → Published (all platforms succeed)
- Publishing → Partially Published (some platforms succeed, others fail)
- Publishing → Failed (all platforms fail)
- Publishing → Unknown (external state cannot be determined)

**Business Rules:**
- Publishing eligibility gate enforced (BR-004, BR-005, BR-006, Section 26)
- Multi-platform results tracked independently (BR-010)
- Platform results cannot overwrite each other (BR-011)
- Failed operations not represented as successful (BR-013)
- Unknown state represented explicitly (BR-018)

---

**State:** Published  
**Entry Condition:** All target platforms confirm successful publication  
**Exit Condition:** Terminal state (content remains published)  
**Business Rules:**
- Publishing confirmed by platform response (Section 32)
- Result recorded with platform details (Section 34)
- Publishing traceable from creation (Section 10)

---

**State:** Partially Published  
**Entry Condition:** Some platforms succeed, others fail  
**Exit Condition:** May remain partially published, or failed platforms may be retried  
**Business Rules:**
- Independent platform results (BR-010, BR-011)
- Successful platform results not overwritten (BR-011)
- Failed platforms may be retried with bounded retries (BR-012)

---

**State:** Failed  
**Entry Condition:** Critical failure at any stage (research, generation, review, validation, publishing)  
**Exit Condition:** May return to appropriate state for retry/correction, or remain failed  
**Business Rules:**
- Failed state recorded accurately (BR-013)
- Failure diagnostics preserved (Sections 14, 16, 36)
- Failed mandatory gates block advancement (BR-004)

---

**State:** Intervention Required  
**Entry Condition:** Revision limit exhausted (BR-003)  
**Exit Condition:** User manually resolves issue  
**Business Rules:**
- Automated revision stopped (Section 21)
- Automatic publishing blocked (Section 21)
- Reason recorded (Section 21)
- User notified (implied by intervention state)

---

### Invalid State Transitions

The following transitions are **prohibited** by business rules:

- Draft → Published (must go through all quality gates)
- Generated → Validated (must complete both AI reviews)
- Under Review → Approved (must complete validation)
- Validated → Published (must be approved and scheduled where required)
- Failed Review → Published (failed gate blocks publication per BR-004)
- Unapproved → Published (approval required per BR-006)
- Any bypass of mandatory AI reviews (BR-002)

Invalid transitions SHALL be rejected by the system (Section 11).

A failed stage shall never silently advance content (Section 11).

## 2.4.5 AI Governance Rules

This section analyzes business rules specifically governing AI operations, ensuring bounded automation and human oversight.

### Mandatory AI Quality Gates

**Governance Principle:** AI automation operates within explicit quality controls.

**Mandatory Gates (BR-002, BR-004):**
1. **AI Review #1:** Mandatory after generation, cannot be bypassed
2. **AI Review #2:** Mandatory after correction, cannot be bypassed
3. **Final Validation:** Mandatory before approval
4. **Approval:** Required where configured before publication

**Enforcement:**
- Generation → Review #1 → Correction → Review #2 → Validation → Approval → Publishing
- No shortcuts or bypasses permitted
- Failed gate blocks publication (BR-004)
- Automation cannot circumvent gates (Section 76)

**Related Business Rules:**
- BR-002 (Mandatory AI Review Sequence)
- BR-004 (Failed Quality Gates Block Publication)

---

### Bounded AI Revision Loops

**Governance Principle:** AI correction/review loops must terminate.

**Finite Loop Enforcement (BR-003):**
- Maximum revision count configured and enforced (Section 21)
- Revision counter maintained per content item
- Counter incremented on each correction attempt
- When limit exhausted:
  - Automated revision STOPS
  - Automatic publishing BLOCKED
  - Workflow enters intervention state
  - Human intervention required

**No Unbounded Autonomous Correction:** System architecture prohibits unlimited AI retry loops (Section 21).

**Related Business Rules:**
- BR-003 (Finite AI Revision Loops)

---

### AI Cannot Bypass Mandatory Controls

**Governance Principle:** Automation cannot bypass quality, validation, authorization, or publishing controls.

**Prohibited Bypasses:**
- AI cannot approve content without human approval where required
- AI cannot bypass mandatory reviews
- AI cannot bypass validation
- AI cannot bypass authorization
- AI cannot bypass publishing eligibility checks
- AI cannot override bounded revision limits

**Explicit Requirement (Section 76):**
"No automated component may bypass a mandatory quality, validation, authorization, or publishing control merely because doing so would make the workflow faster."

**Related Business Rules:**
- BR-002 (Mandatory reviews)
- BR-003 (Bounded revisions)
- BR-004 (Gates block publication)
- BR-005 (Validation required)
- BR-006 (Approval required)

---

### AI Failure Safety

**Governance Principle:** AI failures must be handled safely without fabricating results.

**Failure Handling Rules:**
- Research failure blocks dependent generation (Section 14)
- Never fabricate research results (Section 14, BR-013)
- Generation failure blocks review (Section 16)
- Never treat generation failures as success (Section 16, BR-013)
- Review failure invokes bounded revision (Section 20, BR-003)
- Unknown AI results represented explicitly (BR-018)

**Related Business Rules:**
- BR-013 (Accurate Failure Representation)
- BR-018 (Unknown State Represented Explicitly)

---

### Version Integrity in AI Workflows

**Governance Principle:** AI reviews and corrections operate on correct versions.

**Version Rules:**
- Each review operates on known content version (Section 17)
- Review #2 shall not operate on obsolete version (Section 20)
- Correction creates new version without erasing history (Section 19)
- Approval tied to specific version (BR-007)
- Material edits invalidate approval (BR-007)

**Traceability Requirements (Section 19):**
System shall preserve enough history to determine:
- Original generated content
- Review findings
- Correction input
- Corrected output

**Related Business Rules:**
- BR-007 (Material Edits Invalidate Approval)

---

### Human Oversight Requirements

**Governance Principle:** Human oversight maintained through approval gates.

**Manual Approval:**
- Authorized user approves content before publication (where required) (BR-006)
- User inspects content, research, reviews, and validation results (Section 25)
- Approval decision recorded and auditable (Section 25)

**Automated Validation Alternative:**
- Automated validation permitted where configured (Section 24)
- Must still apply explicitly defined business rules (Section 24)
- Does not bypass quality reviews (BR-002)

**Campaigns:**
- Recurring campaigns must not bypass approval where required (BR-014)
- Each campaign content item individually traceable (Section 30)

**Related Business Rules:**
- BR-006 (Approval Required for Publication)
- BR-014 (Campaigns Must Not Bypass Quality Workflow)

## 2.4.14 Rule Conflict Analysis

This section examines potential conflicts or ambiguities between business rules.

### Potential Conflict 1: Campaign Approval Requirement

**Involved Rules:**
- BR-006 (Approval Required for Publication — "where approval is required")
- BR-014 (Campaigns Must Not Bypass Quality Workflow)

**Potential Ambiguity:**
Does "where approval is required" mean campaigns can be configured to skip manual approval and use automated validation instead?

**Requirements Analysis:**
- Section 25 indicates manual approval is required "where manual approval is required"
- Section 24 mentions validation "may include automated checks, manual review, or both"
- Section 30 states campaigns "shall not bypass review, validation, approval, or publishing gates"

**Resolution:**
Requirements suggest automated validation may be an alternative to manual approval for some workflows, but this is not fully specified. **Unresolved decision:** When manual approval is required vs. automated validation sufficient.

**No Conflict:** Both rules can coexist if campaign configuration specifies approval mode.

---

### Potential Conflict 2: Retry After Eligibility Loss

**Involved Rules:**
- BR-008 (Scheduled Content Revalidation at Execution Time)
- BR-012 (Bounded Publishing Retries)

**Potential Ambiguity:**
If scheduled content becomes ineligible at execution time, does this consume a retry attempt?

**Requirements Analysis:**
- Section 29 says scheduler "re-checks publication eligibility"
- Section 27 says scheduler "refuses publication until eligibility is restored"
- Section 37 says "retry shall re-check content eligibility"

**Resolution:**
Eligibility check is distinct from publishing retry. Eligibility failure should not consume retry counter; it prevents publishing attempt altogether.

**No Conflict:** Eligibility check precedes publishing attempt; ineligibility prevents attempt rather than failing it.

---

### Potential Conflict 3: Unknown State vs. Retry Logic

**Involved Rules:**
- BR-018 (Unknown External State Represented Explicitly)
- BR-012 (Bounded Publishing Retries)

**Potential Ambiguity:**
If publishing result is unknown, should system retry?

**Requirements Analysis:**
- Section 47 says unknown state "shall never be silently converted to success or failure"
- Section 37 discusses retry behavior depending on "failure type"
- Unknown is neither success nor failure

**Resolution:**
Unknown state is a distinct outcome requiring investigation. Automatic retry may not be appropriate for unknown states. **Unresolved decision:** How unknown publishing states are resolved (manual investigation, query API, retry, or wait?).

**Potential Conflict:** Retry logic assumes known failure, but unknown state is ambiguous.

---

### Potential Conflict 4: Material Edit Definition

**Involved Rules:**
- BR-007 (Material Edits Invalidate Approval)
- FR-004 (Content Editing at Permitted Lifecycle States)

**Potential Ambiguity:**
Exact definition of "material edit" not specified.

**Requirements Analysis:**
- Section 12: "material edit after approval shall invalidate approval when the previous approval no longer applies"
- Section 23: "editing shall not silently preserve approval for materially different content"
- Exact criteria not defined

**Resolution:**
**Unresolved decision:** Exact definition of material vs. non-material edit (Section 74 does not list this, but it should be resolved during design).

**No Conflict:** Rule is clear that material edits invalidate approval; only the exact definition of "material" requires clarification.

---

### Confirmed: No Rule Conflicts

Analysis confirms that BR-001 through BR-018 do not contradict each other. All rules are internally consistent and traceable to requirements. Identified ambiguities are unresolved design decisions, not conflicts.
