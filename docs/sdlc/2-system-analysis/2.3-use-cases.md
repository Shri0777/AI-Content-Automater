## 2.3.1 Purpose and Scope

### Purpose

This document establishes the **Use Case Analysis** for the AI Content Automater system. It defines WHAT users and external actors need to accomplish with the system and HOW those interactions conceptually occur.

- **Comprehensive** — Covers all V1 functional interactions including normal flows, alternative flows, and failure scenarios

## 2.3.2 Use Case Modeling Principles

### What is a Use Case?

A use case describes a meaningful goal-oriented interaction between an actor and the system. Each use case represents:

1. **Who** initiates the interaction (Primary Actor)
2. **Why** the interaction occurs (Goal)
3. **What** must be true before starting (Preconditions)
4. **How** the interaction normally proceeds (Main Success Flow)
5. **What** can go wrong (Alternative/Exception Flows)
6. **What** is true after success (Postconditions)
7. **What** governs the interaction (Business Rules)
8. **How** it traces to requirements (Requirement Traceability)

### Modeling Approach

**Actor-Centric:** Use cases are organized by the actor's perspective and goals, not system internals.

**Goal-Oriented:** Each use case achieves a meaningful goal. Avoid overly granular use cases that represent implementation steps.

**Black-Box:** Use cases describe system behavior from the outside. Internal mechanisms (database queries, task queues, framework calls) are not described unless explicitly required by requirements.

**Failure-Aware:** Alternative and exception flows are first-class. Every use case considers what can go wrong and how the system responds.

**Traceable:** Every use case maps to functional requirements and business rules.

### Use Case Template

Each use case follows this structure:

- **Use Case ID** — Stable identifier (UC-NNN)
- **Use Case Name** — Brief descriptive name
- **Primary Actor** — Actor who initiates and has the goal
- **Supporting Actors / External Systems** — Other actors involved
- **Goal** — What the primary actor wants to accomplish
- **Trigger** — What initiates the use case
- **Preconditions** — What must be true before starting
- **Postconditions** — What is true after successful completion
- **Main Success Flow** — Step-by-step normal scenario
- **Alternative Flows** — Variations from the main flow
- **Exception / Failure Flows** — Error conditions and system response
- **Business Rules Involved** — Applicable BR-NNN rules
- **Related Functional Requirements** — Applicable FR-NNN requirements
- **Related Non-Functional Requirements** — Applicable NFR-NNN requirements (where relevant)
- **Data/Entities Involved** — Conceptual data elements (not database tables)
- **Security/Authorization Considerations** — Access control implications
- **State/Lifecycle Implications** — Impact on content lifecycle
- **Dependencies** — Other use cases or systems required
- **Open Questions / Unspecified Decisions** — Items requiring design-time resolution

## 2.3.3 Actors Used in the Use-Case Model

Based on REQUIREMENTS.MD Section 6 and 2.2 Functional Requirements Analysis, the following actors interact with the system:

### Human Actors

#### User
**Definition:** Normal authenticated user managing their own content, schedules, campaigns, integrations, and publishing activity (REQUIREMENTS.MD Section 6.1).

**Goals:**
- Create and manage social media content
- Automate recurring content production
- Publish content to social platforms
- Monitor content performance
- Maintain quality standards

**Characteristics:**
- Owns content, campaigns, and platform connections
- Subject to authorization rules (BR-001)
- Cannot access other users' resources without permission

#### Administrator
**Definition:** User with elevated privileges managing system configuration, users, integrations, and operational information (REQUIREMENTS.MD Section 6.2).

**Goals:**
- Manage system configuration
- Manage users and permissions
- Monitor system operations
- Configure integrations

**Characteristics:**
- Has administrative authorization
- Access is auditable (Section 9)
- Deliberate and controlled access to user resources

### External System Actors

#### AI Service
**Definition:** Configured AI provider supplying generation, review, and correction capabilities (REQUIREMENTS.MD Section 6.3).

**Responsibilities:**
- Generate content based on prompts
- Perform quality reviews
- Suggest or apply corrections

**Characteristics:**
- External dependency
- Subject to availability, rate limits, and errors
- Requires configuration

#### Scheduler
**Definition:** Internal scheduling subsystem identifying work whose execution time has arrived (REQUIREMENTS.MD Section 6.4).

**Responsibilities:**
- Identify due scheduled work
- Trigger campaign execution at configured times
- Initiate publishing at scheduled times

**Characteristics:**
- Internal system process
- Time-driven execution
- Must prevent duplicate execution

#### Publishing Integration
**Definition:** Platform integration submitting approved content and reporting platform result (REQUIREMENTS.MD Section 6.5).

**Responsibilities:**
- Translate content to platform-specific format
- Submit content to social platform API
- Report publishing results

**Characteristics:**
- One integration per platform
- Platform-specific limitations
- Independent operation per platform (BR-010, BR-011)

#### Research Source
**Definition:** Configured source providing information used by research (REQUIREMENTS.MD Section 6.6).

**Responsibilities:**
- Provide research information for topics

**Characteristics:**
- External dependency
- May be multiple sources
- Subject to availability

### UC-001: Authenticate User

**Use Case ID:** UC-001  
**Use Case Name:** Authenticate User  
**Primary Actor:** User  
**Supporting Actors:** None  
**Goal:** User gains authenticated access to the system

**Trigger:** User attempts to access protected functionality

**Preconditions:**
- User has valid account credentials
- Authentication system is operational

**Main Success Flow:**
1. User provides credentials (username/email and password)
2. System validates credentials against stored user record
3. System verifies password using secure framework storage
4. System creates authenticated session with secure session controls
5. System grants access to protected functionality
6. System records authentication event in audit log

**Alternative Flows:**

*A1: Invalid Credentials*
- At step 2: Credentials do not match any user record
- System rejects authentication attempt
- System does not disclose whether username or password was incorrect
- System may implement rate limiting to prevent brute force (implementation detail)
- User receives generic authentication failure message
- Use case ends in failure

**Exception / Failure Flows:**

*E1: Account Locked or Disabled*
- At step 2: User account exists but is locked, disabled, or deleted
- System denies access with appropriate message
- System records authentication attempt in audit log
- Use case ends in failure

*E2: Session Creation Failure*
- At step 4: System cannot create session
- System denies access
- System logs error
- User receives error message
- Use case ends in failure

*E3: Authentication System Unavailable*
- At step 2: Authentication system is unavailable
- System denies access
- System logs error
- User receives error message
- Use case ends in failure

**Postconditions:**
- **Success:** User has authenticated session and can access protected functionality
- **Failure:** User remains unauthenticated and cannot access protected functionality

**Business Rules Involved:**
- BR-001: Users cannot access another user's protected resources without authorization

**Related Functional Requirements:**
- FR-001: Authentication

**Related Non-Functional Requirements:**
- NFR-001: Security — Protected resources and secrets must be secured

**Data/Entities Involved:**
- User account
- Credentials
- Session
- Audit log

**Security/Authorization Considerations:**
- Passwords use framework's secure password storage (Section 7)
- Sessions use secure application controls (Section 7)
- Authentication failures shall not disclose sensitive information (Section 7)
- Unauthenticated users shall not access private content, schedules, publishing information, credentials, or administration (Section 7)

**State/Lifecycle Implications:**
- User transitions from unauthenticated to authenticated state

**Dependencies:**
- None (foundational use case)

**Open Questions / Unspecified Decisions:**
- Exact rate limiting strategy for brute force prevention
- Session timeout duration
- Multi-factor authentication support (not mentioned in requirements)

### UC-002: Authorize Resource Access

**Use Case ID:** UC-002  
**Use Case Name:** Authorize Resource Access  
**Primary Actor:** User (authenticated)  
**Supporting Actors:** Administrator (for administrative access)  
**Goal:** System enforces access control for protected resources

**Trigger:** Authenticated user requests access to a resource

**Preconditions:**
- User is authenticated (UC-001)
- Resource exists and has defined ownership or access control

**Main Success Flow:**
1. Authenticated user requests access to a resource (content, schedule, campaign, etc.)
2. System identifies resource owner and access control rules
3. System checks user's authorization level:
   - User owns the resource, OR
   - User has explicit permission to access resource, OR
   - User has administrative authorization for the resource type
4. System determines user is authorized
5. System grants access to resource
6. System logs authorization decision for sensitive operations

**Alternative Flows:**

*A1: Unauthorized Access Attempt*
- At step 3: User does not own resource and has no explicit permission
- System denies access
- System returns appropriate error (HTTP 403 Forbidden or equivalent)
- System does not expose protected data
- System logs unauthorized access attempt for sensitive resources
- Use case ends in failure

*A2: Administrative Access*
- At step 3: User has administrative authorization for resource type
- System verifies administrative authorization is appropriate for the operation
- System grants access
- System records administrative access in audit log (Section 9)
- Access is auditable and deliberate
- Use case continues

*A3: Resource Not Found*
- At step 2: Resource does not exist
- System returns not-found error (HTTP 404 or equivalent)
- System does not disclose whether resource exists for another user
- Use case ends in failure

**Exception / Failure Flows:**

*E1: Authorization System Failure*
- At step 3: Authorization check fails due to system error
- System denies access (fail-safe)
- System logs error
- System does not expose protected data
- Use case ends in failure

*E2: Insecure Direct Object Reference Attempt*
- At step 1: User modifies identifier/URL/parameter to access another user's resource
- System enforces ownership check at step 3
- System denies access
- System logs suspicious activity
- Use case ends in failure

**Postconditions:**
- **Success:** User has authorized access to resource and can perform permitted operations
- **Failure:** User is denied access and cannot access resource

**Business Rules Involved:**
- BR-001: Users cannot access another user's protected resources without authorization

**Related Functional Requirements:**
- FR-002: Authorization

**Related Non-Functional Requirements:**
- NFR-001: Security — Protected resources must be secured

**Data/Entities Involved:**
- User account
- Resource (content, research, version, review, approval, schedule, campaign, publishing job, platform connection, media, notification, analytics, audit record)
- Ownership relationship
- Access control rules

**Security/Authorization Considerations:**
- Authorization shall be enforced server-side (Section 8)
- Users shall access only resources they own or are explicitly permitted to access (Section 8)
- Administrative operations shall require appropriate administrative authorization (Section 8)
- Hiding a UI control shall never be the only authorization mechanism (Section 8)
- Unauthorized requests shall fail safely without exposing protected data (Section 8)
- The system shall prevent insecure direct object access (Section 9)
- Changing an identifier, URL, or request parameter shall not allow access to another user's resources (Section 9)
- Background tasks shall preserve ownership context (Section 9)

**State/Lifecycle Implications:**
- None (authorization check does not change state)

**Dependencies:**
- UC-001: Authenticate User (must be authenticated first)

**Open Questions / Unspecified Decisions:**
- Exact role hierarchy beyond User/Administrator
- Granularity of permission system (resource-level, operation-level, etc.)
- Shared resource access model (if any)

### UC-003: Manage User Session

**Use Case ID:** UC-003  
**Use Case Name:** Manage User Session  
**Primary Actor:** User (authenticated)  
**Supporting Actors:** None  
**Goal:** User maintains authenticated session or explicitly ends session

**Trigger:** User performs authenticated activities or initiates logout

**Preconditions:**
- User is authenticated (UC-001)
- Active session exists

**Main Success Flow:**

*Session Maintenance:*
1. User performs operations within session
2. System validates session on each request
3. System extends session if within validity period
4. System maintains secure session state

*Explicit Logout:*
1. User initiates logout
2. System terminates user session
3. System clears session data
4. System records logout event in audit log
5. User becomes unauthenticated

**Alternative Flows:**

*A1: Session Timeout*
- During session maintenance: Session expires due to inactivity timeout
- System invalidates session
- System requires re-authentication for next protected request
- User must execute UC-001 to re-authenticate

**Exception / Failure Flows:**

*E1: Session Invalid or Tampered*
- At session validation: Session token is invalid or tampered
- System rejects session
- System treats user as unauthenticated
- System may log security event
- User must execute UC-001 to re-authenticate

*E2: Concurrent Session Handling*
- User logs in from multiple locations/devices
- System behavior depends on configuration (not specified in requirements)
- Possible behaviors: Allow concurrent sessions, invalidate previous session, or deny new session

**Postconditions:**
- **Success (Maintenance):** Session remains valid and user continues authenticated
- **Success (Logout):** Session terminated and user is unauthenticated
- **Failure:** Session invalid and user must re-authenticate

**Business Rules Involved:**
- BR-001: Users cannot access another user's protected resources without authorization (session ties user to authorization)

**Related Functional Requirements:**
- FR-001: Authentication

**Related Non-Functional Requirements:**
- NFR-001: Security — Sessions must be secure

**Data/Entities Involved:**
- User session
- Session state
- Audit log

**Security/Authorization Considerations:**
- Sessions shall use secure application controls (Section 7)
- The system shall provide secure login and logout behavior (Section 7)

**State/Lifecycle Implications:**
- User authenticated state duration

**Dependencies:**
- UC-001: Authenticate User (creates session)

**Open Questions / Unspecified Decisions:**
- Session timeout duration
- Concurrent session policy
- Session renewal behavior
- "Remember me" functionality (not mentioned in requirements)

### UC-004: Create Content Item

**Use Case ID:** UC-004  
**Use Case Name:** Create Content Item  
**Primary Actor:** User (authenticated)  
**Supporting Actors:** None  
**Goal:** User creates a new content item for social media publication

**Trigger:** User initiates content creation action

**Preconditions:**
- User is authenticated (UC-001)
- User is authorized to create content (UC-002)

**Main Success Flow:**
1. User initiates content creation
2. User provides content information:
   - Title or internal name (optional per Section 10)
   - Topic
   - User instructions for generation
   - Target platform(s)
3. User optionally associates media
4. System creates content item in Draft state
5. System associates content with owning user
6. System records creation timestamp and ownership metadata
7. System returns content identifier to user
8. Content available for further workflow actions

**Alternative Flows:**

*A1: User Provides Research References*
- At step 2: User provides existing research references or initiates research
- System associates research with content
- Continue to step 4

*A2: User Provides Pre-Written Content*
- At step 2: User provides manually written content instead of generation instructions
- Content marked as manually created
- May skip AI generation workflow
- Continue to step 4

**Exception / Failure Flows:**

*E1: Invalid Input*
- At step 2: User provides invalid or incomplete required data
- System validates input (Section 55)
- System returns validation errors
- User corrects input and retries
- Use case returns to step 2

*E2: Authorization Failure*
- At step 1: User lacks permission to create content
- System denies operation per BR-001
- Use case ends in failure

**Postconditions:**
- **Success:** New content item exists in Draft state, owned by user, with unique identifier
- **Failure:** No content item created

**Business Rules Involved:**
- BR-001: Users cannot access another user's protected resources without authorization (user owns created content)

**Related Functional Requirements:**
- FR-003: Content Creation

**Related Non-Functional Requirements:**
- NFR-001: Security — Ownership established

**Data/Entities Involved:**
- Content item (Section 10):
  - Title/internal name
  - Topic
  - User instructions
  - Target platforms
  - Research references (optional)
  - Media (optional)
  - Ownership
  - Timestamps
  - Lifecycle status (Draft)

**Security/Authorization Considerations:**
- Content ownership established at creation (Section 9)
- User can only create content under their own ownership
- Every user-owned resource has clear ownership relationship (Section 9)

**State/Lifecycle Implications:**
- Content enters Draft state
- Beginning of content lifecycle (Section 11)

**Dependencies:**
- UC-001: Authenticate User (must be authenticated)
- UC-002: Authorize Resource Access (must be authorized)

**Open Questions / Unspecified Decisions:**
- Exact required vs. optional fields for content creation
- Whether content can be created in shared/collaborative mode
- Content templates or presets (not mentioned in requirements)

### UC-005: Edit Content Item

**Use Case ID:** UC-005  
**Use Case Name:** Edit Content Item  
**Primary Actor:** User (authenticated and authorized)  
**Supporting Actors:** None  
**Goal:** User modifies existing content while maintaining version history and approval integrity

**Trigger:** User initiates edit action on content item

**Preconditions:**
- User is authenticated (UC-001)
- User is authorized to edit the content (UC-002)
- Content exists
- Content is in lifecycle state that permits editing (Section 23)

**Main Success Flow:**
1. User requests to edit content
2. System verifies user owns content or has edit permission
3. System verifies content lifecycle state permits editing
4. User modifies content:
   - Content text
   - Topic
   - Instructions
   - Target platforms
   - Media associations
   - Other editable attributes
5. System creates new version or revision
6. System preserves relationship between previous and edited versions
7. System records editor, timestamp
8. System evaluates if edit is material (affects approval)
9. If edit is non-material: Content state unchanged
10. System saves changes

**Alternative Flows:**

*A1: Material Edit After Approval*
- At step 8: System detects material edit to approved content
- System invalidates previous approval (BR-007)
- System returns content to appropriate quality gate (Section 23)
- System records approval invalidation
- User notified that re-approval required
- Content state changes from Approved to earlier state

*A2: Edit Returns Content to Review*
- At step 8: Material edit requires re-review
- System returns content to AI Review workflow
- Content state changes appropriately

**Exception / Failure Flows:**

*E1: Edit Not Permitted at Current State*
- At step 3: Content is in state that does not permit editing (e.g., Publishing, Published)
- System denies edit operation
- System provides appropriate message explaining state restriction
- Use case ends in failure

*E2: Authorization Failure*
- At step 2: User does not own content and lacks edit permission
- System denies operation per BR-001
- Use case ends in failure

*E3: Concurrent Edit Conflict*
- At step 10: Another user has modified content concurrently
- System detects version conflict
- System provides conflict resolution options
- User resolves conflict or retries

**Postconditions:**
- **Success:** Content updated with new version, history preserved, approval status adjusted if needed
- **Failure:** Content unchanged

**Business Rules Involved:**
- BR-001: Users cannot access another user's protected resources without authorization
- BR-007: Material edits invalidate affected approval

**Related Functional Requirements:**
- FR-004: Content Editing

**Related Non-Functional Requirements:**
- NFR-008: Data Integrity — Version history preserved

**Data/Entities Involved:**
- Content item (current version)
- Content version history
- Previous version reference
- Edit metadata (author, timestamp)
- Approval records (potentially invalidated)

**Security/Authorization Considerations:**
- Ownership verified before edit (BR-001)
- Editing shall not silently preserve approval for materially different content (Section 23)
- An edit that invalidates review or approval shall return content to appropriate quality gate (Section 23)

**State/Lifecycle Implications:**
- May remain in current state (non-material edit)
- May return to earlier state (material edit invalidates approval)
- May return to Review or Validation state

**Dependencies:**
- UC-001: Authenticate User
- UC-002: Authorize Resource Access
- UC-013: Approve Content (approval may be invalidated)

**Open Questions / Unspecified Decisions:**
- Exact definition of "material edit" (Section 74 does not list, but should be resolved)
- Which specific edits invalidate approval vs. preserve it
- Concurrent edit resolution strategy
- Edit permission granularity beyond ownership

### UC-006: Collect Research for Content

**Use Case ID:** UC-006  
**Use Case Name:** Collect Research for Content  
**Primary Actor:** User (manual initiation) or Campaign Automation (automated initiation)  
**Supporting Actors:** Research Source (external system), Scheduler (for automated campaigns)  
**Goal:** System collects research information from configured sources to inform content generation

**Trigger:** User initiates research, or automated campaign triggers research

**Preconditions:**
- Research sources are configured (Section 51)
- Content item exists for research association
- Research sources are accessible

**Main Success Flow:**
1. System receives research request for content topic
2. System identifies configured research sources for topic
3. System queries one or more external research sources (Section 13)
4. Research sources return information
5. System validates and processes responses
6. System records research results including:
   - Source title
   - Source URL or identifier
   - Retrieved information
   - Retrieval timestamp
   - Source metadata
   - Permitted excerpts or structured information (Section 13)
7. System associates research records with content item
8. Research results remain distinguishable from generated content (Section 13)
9. System marks research as complete
10. Content proceeds to generation or next workflow stage

**Alternative Flows:**

*A1: Multiple Research Sources*
- At step 3: System queries multiple sources
- Each source returns independent results
- System aggregates results from all sources
- All sources recorded with traceability

*A2: Partial Research Success*
- At step 4: Some sources succeed, others fail
- System records successful research results
- System records which sources failed
- Decision: Proceed with partial research or fail entirely (not specified)

**Exception / Failure Flows:**

*E1: Required Research Fails (Section 14)*
- At step 4: Required research source fails
- System records the failure
- System preserves useful diagnostics
- System does NOT mark research successful (BR-013)
- System prevents dependent generation when research is mandatory (Section 14)
- System exposes actionable failure state
- User notified of research failure
- Use case ends in failure

*E2: Transient Research Failure with Retry*
- At step 4: Research fails with transient error
- System uses bounded retries (Section 14)
- System attempts retry after delay
- If retry succeeds: Continue to step 5
- If retries exhausted: Treat as E1 (Required Research Fails)

*E3: Research Source Unavailable*
- At step 3: Research source is down or unreachable
- System records unavailability
- System applies retry logic if transient
- If mandatory: Blocks generation per Section 14
- Use case ends in failure or proceeds with available sources

*E4: Invalid or Malformed Research Response*
- At step 5: Research source returns invalid data
- System validates response
- Invalid response treated as failure
- System does NOT fabricate research results (Section 14)
- Recorded as failure

**Postconditions:**
- **Success:** Research records associated with content, traceable sources recorded, ready for generation
- **Failure:** Research marked failed, generation blocked if research mandatory, diagnostics preserved

**Business Rules Involved:**
- BR-013: Failed external operations must not be represented as successful

**Related Functional Requirements:**
- FR-005: Research

**Related Non-Functional Requirements:**
- NFR-002: Reliability — Safe failure handling
- NFR-005: Observability — Diagnosable failures

**Data/Entities Involved:**
- Research record (Section 13):
  - Source title
  - Source URL or identifier
  - Retrieved information
  - Retrieval timestamp
  - Source metadata
  - Permitted excerpts or structured information
- Content association
- Failure diagnostics (if failed)

**Security/Authorization Considerations:**
- Research associated with user-owned content (BR-001)
- Research sources may require API credentials (stored securely per BR-016)

**State/Lifecycle Implications:**
- Content transitions from Draft to Researching
- On success: Ready for Generation
- On failure: Remains in Researching or returns to Draft

**Dependencies:**
- UC-004: Create Content Item (content must exist)
- External research sources configured
- Network connectivity to research sources

**Open Questions / Unspecified Decisions:**
- Exact research providers (Section 74)
- Research source types and mechanisms
- Whether research is mandatory or optional per content type
- Behavior when partial research succeeds (some sources fail)
- Research result storage limits

## 2.3.7 AI Generation & Quality Control Use Cases

### UC-007: Generate Content with AI

**Use Case ID:** UC-007  
**Use Case Name:** Generate Content with AI  
**Primary Actor:** User (manual request) or Campaign Automation (automated trigger)  
**Supporting Actors:** AI Service (external system), Background Task Executor, Scheduler (for campaigns)  
**Goal:** System generates social media content using configured AI service

**Trigger:** User requests content generation, or automated campaign triggers generation

**Preconditions:**
- AI provider is configured (Section 51)
- Content item exists with required inputs:
  - Topic
  - User instructions
  - Research results (if available/required)
  - Target platform
  - Desired format
- AI provider is accessible

**Main Success Flow:**
1. System receives generation request
2. System prepares generation input (Section 15):
   - Topic
   - User instructions
   - Research results
   - Target platform
   - Desired format
   - Configured content rules
   - Explicitly permitted context
3. System submits request to configured AI provider/model
4. AI provider processes request
5. AI provider returns generated content
6. System validates response format
7. System stores generated content
8. System associates generation with content item and version
9. Generated content marked distinguishable from manual edits (Section 15)

### UC-021: Retry Failed Publishing

**Use Case ID:** UC-021

5. System checks retry count against maximum (Section 37, BR-012)
6. Under retry limit
7. System schedules retry with appropriate delay
8. System maintains stable job identity for duplicate detection (Section 35)
9. Retry executes:
   - System re-checks content eligibility (Section 37)
   - System attempts publication again
   - System uses duplicate-publication protection (BR-012)
10. System records retry result
11. If success: Publishing complete
12. If failure: Return to step 4 (check limit again)

**Alternative Flows:**

- At step 8: Platform provides idempotency mechanisms
- Integration uses platform idempotency (Section 35)
- Duplicate publication prevented by platform
- Continue to step 9

*A2: Application-Level Duplicate Prevention*
- At step 8: Platform lacks idempotency support
- System uses state locking and uniqueness constraints (Section 35)
- Continue to step 9

**Exception / Failure Flows:**

*E1: Retry Limit Exhausted*
- At step 5: Retry count equals or exceeds maximum
- System does NOT retry (Section 37)
- Publishing marked permanently failed
- User notified
- Use case ends with permanent failure

*E2: Non-Retryable Failure*
- At step 2: Failure is permanent (invalid content, deleted account, etc.)
- System does NOT retry
- Publishing marked permanently failed
- Use case ends with permanent failure

*E3: Authentication Failure*
- At step 2: Platform credentials invalid/expired
- Authentication failures NOT retried as ordinary API failures (Section 37)
- User notified to re-authorize
- Publishing blocked until re-authorization
- Use case ends in failure

*E4: Content Becomes Ineligible During Retry*
- At step 9: Eligibility re-check fails
- Content no longer eligible
- Retry aborted
- Use case ends in failure

*E5: Duplicate Detected*
- At step 9: System detects duplicate publishing attempt
- Duplicate prevented (BR-012)
- System retrieves existing result
- Use case ends (duplicate prevented)

**Postconditions:**
- **Success:** Publishing succeeds after retry, result recorded
- **Failure (Retryable):** Will retry again if under limit
- **Failure (Exhausted):** Permanently failed, no more retries

**Business Rules Involved:**
- BR-012: Publishing retries must be bounded and duplicate-safe

**Related Functional Requirements:**
- FR-017: Publishing Retry

**Related Non-Functional Requirements:**
- NFR-002: Reliability

**Data/Entities Involved:**

**Security/Authorization Considerations:**
- Retries preserve ownership context (BR-017)

**State/Lifecycle Implications:**
- Content in Retrying state
- Eventually Published or Failed

**Dependencies:**
